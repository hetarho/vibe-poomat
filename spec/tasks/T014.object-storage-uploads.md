# T014 object storage & presigned uploads
> st:todo | ssot:ARCH-37 ARCH-17 ARCH-41 ARCH-29 | base:ARCH@2 | dep:T006

## goal
S3-compatible storage behind a `FileStorage` port with browser-direct presigned uploads, so avatars and cover images never pass through the api.

## acceptance
- [ ] `FileStorage` port: `createUploadUrl({ key, contentType, maxBytes })` → `{ url, fields?, publicUrl }`, `delete(key)`, `publicUrl(key)`; S3 adapter using `@aws-sdk/client-s3` + `@aws-sdk/s3-request-presigner` (works against both R2 and MinIO)
- [ ] `minio` service added to `docker-compose.yml` with a bucket created at startup; config keys `S3_ENDPOINT` `S3_BUCKET` `S3_ACCESS_KEY_ID` `S3_SECRET_ACCESS_KEY` `S3_PUBLIC_BASE_URL`
- [ ] `POST /api/v1/uploads` (authenticated once T019 lands; until then guarded by the throttler only) returns a presigned URL for a caller-declared purpose (`avatar` | `project-cover`) — the server derives the key, the client never proposes one
- [ ] presign policy enforces content-type allowlist (image/png, image/jpeg, image/webp) and a 2MB cap; a mismatching upload is rejected by the storage service, not only by the UI
- [ ] keys are `<purpose>/<uuidv7>.<ext>`; the api stores the key, never a full URL, and renders public URLs through `publicUrl(key)`
- [ ] presign URLs expire in 5 minutes; the endpoint is rate limited per user/IP (ARCH-41)
- [ ] deleting an entity that owns an image deletes its object best-effort in a job; a failed delete logs and does not fail the use case
- [ ] test (int): presign against a MinIO Testcontainer, upload with the returned URL, read the object back; an upload with a disallowed content-type is refused by the server
- [ ] test: an oversized declared `maxBytes` request is rejected with a 422 `{code}`; key generation never uses client input
- [ ] test: `publicUrl` composes `S3_PUBLIC_BASE_URL` + key and is what the API returns to clients

## impl notes
- presigned PUT (single request) rather than POST policy forms ← simpler client, and R2 supports it identically to MinIO
- the api never proxies bytes (ARCH-37), so no multipart body parsing is configured on Fastify
- image processing (resize/optimize) is out of scope: v1 stores the original and the web layer sizes it with CSS; revisit if bandwidth becomes a problem
- MinIO in compose keeps local parity honest — the alternative (a filesystem adapter for dev) would let S3-only bugs reach production
