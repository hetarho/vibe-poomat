# T008 web data layer
> st:done@260907 | ssot:ARCH-7 ARCH-12 ARCH-16 ARCH-33 ARCH-6 | base:ARCH@2 | dep:T006 T007

## goal
Wire `@repo/api-client` into TanStack Query with SSR-safe hydration, typed error surfacing, and the Zustand store convention.

## acceptance
- [v] a QueryClient is created per SSR request (never module-level) and dehydrated/hydrated through the root route, so no cache crosses requests
- [v] default query options: `staleTime` 30s, `retry` disabled for `ApiError` with a 4xx status, one retry otherwise; mutations never retry
- [v] `src/shared/api`: the api-client instance built from `API_URL` (server) / same-origin (browser) with `credentials:'include'`, plus re-exported `ApiError`
- [v] `src/shared/api/error-message.ts`: maps `ApiError.code` → user-facing copy with a generic fallback; unknown codes never render raw server text
- [v] `src/shared/store`: Zustand pattern (typed `create` wrapper, slice-per-file, selectors exported) used only for cross-slice client state (ARCH-7) — a README-less comment in `index.ts` states the rule
- [v] TanStack Query is the only cache layer; no bespoke in-memory caches (ARCH-33)
- [v] test: a 404 `{code}` response surfaces as `ApiError` and is not retried (retry spy count 0); a 500 retries once
- [v] test: SSR hydration — a prefetched query renders its data on the server and the client mounts without an extra fetch
- [v] test: two sequential SSR renders with different prefetched data do not leak state between QueryClients
- [v] test: `error-message` returns the fallback copy for an unmapped code

## impl notes
- query keys: `[<entity>, <op>, params]` arrays defined next to each feature's api module (`features/<slice>/api`), never inline string keys ← makes invalidation greppable
- SSR fetches run server-side with the incoming `cookie` header forwarded to the api; the browser client relies on the cookie being same-site (ARCH-18 session cookie)
- error copy lives in the web layer, not the api: the api's stable `code` is the contract, the sentence is a UI decision (ARCH-17)
- no global loading/error boundary policy beyond route-level `errorComponent` + `pendingComponent`; features may add local handling

## result
- files: `apps/web/src/router.tsx` · `apps/web/app/routes/__root.tsx` · `apps/web/src/shared/api/{base-url,client,error-message,index}.ts` + `error-message.test.ts` · `apps/web/src/shared/query/{context,query-client,retry,index}.ts` + `retry.test.ts` `hydration.test.tsx` · `apps/web/src/shared/model/{create-store,index}.ts` · `packages/config/src/{env.ts,web.ts,index.ts}` + tests · `packages/config/package.json` (`./web` entry)
- verify: 155 tests pass (root 42 + web 30 + api 80 + api int 3) · `pnpm turbo run lint typecheck test build` 17/17 · Steiger clean · `pnpm biome format --write .` no-op · the built SSR response carries both the rendered content and the `queryState` hydration payload
- **`src/shared/store` became `src/shared/model`.** Steiger's `fsd/segments-by-purpose` rejects a segment named after what it holds, and FSD's vocabulary puts state in `model`. ARCH-6 and ARCH-23 make Steiger authoritative on the layout, so the tool won over the directory name the acceptance sketched; the rule about what may live there is unchanged and now stated in `model/index.ts`
- `@repo/config` gained a **`./web` entry**: `webEnvSchema` is `envSchema.pick({NODE_ENV, LOG_LEVEL, API_URL, WEB_URL})`, so a web server never has to hold `DATABASE_URL` to boot. It is one schema with two entry points, not a second schema — T002's rule holds, and a shared `parseEnvWith` gives both the same error reporting
- `apiBaseUrl()` is **async**: `createServerOnlyFn` plus a dynamic `import('@repo/config/web')` keeps the server config out of the browser bundle, where `process.env` does not exist. The browser branch returns an empty base, so requests are same-origin behind the reverse proxy (ARCH-30) and the session cookie stays same-site (ARCH-18)
- the router hands its dehydrated payload over as a **JSON string**. TanStack Router proves payload serializability structurally, and Query types query keys and cached data as `unknown`, which no structural check can accept — even though `dehydrate` exists precisely to produce JSON. Stringifying is honest and needs no cast; the alternative was casting through `never`
- `credentials: 'include'` is set by `@repo/api-client`'s factory (T006) rather than restated here, so there is one place that decides it
- retry policy is a predicate, not a number: any `ApiError` with a 4xx never repeats, because the server has already said the request itself is wrong; everything else gets exactly one more chance. Mutations never retry, so a side effect cannot double
- the SSR tests exercise the real mechanism rather than a mock of it: one client per simulated request, a prefetch, `renderToString`, then `hydrate(dehydrate(...))` into a second client with a spy query function that is asserted never to run
- no consumers yet: the first query keys arrive with the feature slices (T032+), which is where the `[<entity>, <op>, params]` convention from the impl notes will show up
- no SSOT divergence
