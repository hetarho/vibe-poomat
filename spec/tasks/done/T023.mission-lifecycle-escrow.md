# T023 mission lifecycle & escrow
> st:done@260908 | ssot:PROJ-4 PROJ-5 PROJ-6 PROJ-7 PROJ-13 CRED-3 CRED-5 ARCH-35 ARCH-38 | base:PROJ@2 CRED@2 ARCH@2 | dep:T022 T021 T012

## goal
Missions that escrow credits on open, hold exactly one active mission per project, and close, complete or expire with the right refunds.

## acceptance
- [v] schema `missions(id uuid pk, project_id uuid not null, task_text varchar(1000) not null, questions jsonb not null, slots integer not null, state text not null, opened_at, ended_at, created_at, updated_at, index(project_id), unique(project_id) where state = 'open')`
- [v] `POST /api/v1/projects/:id/missions` (owner only): task text ≤1000, 0-3 questions each ≤200 chars, slots 1-10 (PROJ-13); escrows `slots` credits through the credit context in the same transaction (CRED-3) and fails with `INSUFFICIENT_CREDITS` when the balance is short
- [v] the partial unique index plus an explicit pre-check enforce one open mission per project (PROJ-5) → 409 `{code:"MISSION_ALREADY_OPEN"}`
- [v] mission text, questions, slot count and the project's live URL are immutable while the mission is open (PROJ-7) — no update endpoint exists for them
- [v] `POST /api/v1/missions/:id/close` (owner) → state `closed`, refunds credits for unfilled slots (CRED-5), leaves held/submitted slots alive until they settle (PROJ-6)
- [v] `mission.expire` job scheduled at open time for +30 days: expires the mission and refunds unfilled slots identically; cancelled when the mission ends earlier
- [v] a mission whose last slot settles transitions to `completed` (PROJ-6) — driven by a `SlotSettled` event handler, not by polling
- [v] slot accounting is a single source of truth: `slots` minus (held + submitted + settled) = claimable, computed from the feedback context's claim rows through its application service (no cross-context join, ARCH-14)
- [v] closing/expiring emits `MissionEnded { missionId, refundedSlots }` for NOTI (T030)
- [v] test: unit tests — slots outside 1-10, task text over 1000, 4 questions, non-owner, second open mission all rejected with their codes
- [v] test (int): opening escrows exactly `slots` credits and rolls back both mission row and escrow when the credit call fails
- [v] test (int): close refunds only unfilled slots; a held slot keeps its credit escrowed and refunds later when released
- [v] test (int): the expire job refunds and marks `expired`; running it twice is a no-op; closing before 30 days cancels the job

## impl notes
- missions live in the `project` context (they are the project's request for feedback) while claims/reports live in `feedback` ← keeps the "one open mission per project" invariant enforceable by a DB index instead of a cross-context check
- questions stored as `jsonb` array of strings with the count/length validated in the domain: they are frozen at open time and never queried individually
- the credit call happens through the credit context's application service inside the ambient transaction (ARCH-38), so escrow and mission creation are atomic
- `unique(project_id) where state = 'open'` is the real guard; the pre-check exists only to return a friendly error instead of a constraint violation
- refund amount = slots that were never held or whose hold expired without a submission, computed at end time from the claim rows, never cached on the mission
