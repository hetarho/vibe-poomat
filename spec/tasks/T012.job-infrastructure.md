# T012 pg-boss job infrastructure
> st:todo | ssot:ARCH-35 ARCH-38 ARCH-13 ARCH-32 | base:ARCH@2 | dep:T011

## goal
Delayed and immediate background jobs on the same PostgreSQL, enqueueable atomically with the state change that schedules them.

## acceptance
- [ ] `JobScheduler` port in `src/shared/application`: `enqueue(name, data, opts?)`, `schedule(name, data, runAt)`, `cancel(name, key)`; pg-boss adapter in `src/shared/infrastructure/jobs`
- [ ] enqueue/schedule executed inside the ambient transaction (T011) so a rolled-back use case leaves no job
- [ ] pg-boss started as a Nest lifecycle-managed singleton, its schema created by pg-boss itself (drizzle-kit never generates it and `drizzle-kit generate` ignores the `pgboss` schema)
- [ ] a `JobHandler` registry: one class per job name in the owning context's `application/jobs`, resolved through Nest DI; unknown job name fails loudly at boot, not at runtime
- [ ] jobs carry a `singletonKey` where a duplicate would be harmful, and every handler is idempotent (re-running a completed job is a no-op)
- [ ] retry policy: 3 attempts with exponential backoff, then the job lands in the dead-letter queue and logs at error level with the job name + key
- [ ] worker mode: the same api process runs the workers in v1; a `JOBS_ENABLED` env flag lets a future instance run api-only
- [ ] `/ready` gains a `jobs` indicator (pg-boss started and connected)
- [ ] test (int): a job scheduled inside a rolled-back transaction never runs; the same job in a committed transaction runs once
- [ ] test (int): a handler re-invoked with the same payload produces the same end state (idempotence) using a real handler fixture
- [ ] test (int): a handler throwing 3 times ends dead-lettered and does not retry forever

## impl notes
- job names are dotted and owned by their context: `slot.release` `feedback.warn` `feedback.auto-accept` `mission.expire` `email.send` — the constants live next to the handler, so a later task adds a name without touching this one
- `singletonKey` convention = the aggregate id the job acts on (`feedback:<id>`), so a rescheduled timer replaces rather than duplicates
- cancellation is by singletonKey (e.g. a feedback settled before 72h cancels its auto-accept job); handlers must ALSO re-check state on run, because pg-boss cancellation is best-effort
- timers are scheduled in absolute time (`runAt`), never as "delay from now" computed at handler time ← clock drift across restarts
