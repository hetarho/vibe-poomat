# T012 pg-boss job infrastructure
> st:done@260907 | ssot:ARCH-35 ARCH-38 ARCH-13 ARCH-32 | base:ARCH@2 | dep:T011

## goal
Delayed and immediate background jobs on the same PostgreSQL, enqueueable atomically with the state change that schedules them.

## acceptance
- [v] `JobScheduler` port in `src/shared/application`: `enqueue(name, data, opts?)`, `schedule(name, data, runAt)`, `cancel(name, key)`; pg-boss adapter in `src/shared/infrastructure/jobs`
- [v] enqueue/schedule executed inside the ambient transaction (T011) so a rolled-back use case leaves no job
- [v] pg-boss started as a Nest lifecycle-managed singleton, its schema created by pg-boss itself (drizzle-kit never generates it and `drizzle-kit generate` ignores the `pgboss` schema)
- [v] a `JobHandler` registry: one class per job name in the owning context's `application/jobs`, resolved through Nest DI; unknown job name fails loudly at boot, not at runtime
- [v] jobs carry a `singletonKey` where a duplicate would be harmful, and every handler is idempotent (re-running a completed job is a no-op)
- [v] retry policy: 3 attempts with exponential backoff, then the job lands in the dead-letter queue and logs at error level with the job name + key
- [v] worker mode: the same api process runs the workers in v1; a `JOBS_ENABLED` env flag lets a future instance run api-only
- [v] `/ready` gains a `jobs` indicator (pg-boss started and connected)
- [v] test (int): a job scheduled inside a rolled-back transaction never runs; the same job in a committed transaction runs once
- [v] test (int): a handler re-invoked with the same payload produces the same end state (idempotence) using a real handler fixture
- [v] test (int): a handler throwing 3 times ends dead-lettered and does not retry forever

## impl notes
- job names are dotted and owned by their context: `slot.release` `feedback.warn` `feedback.auto-accept` `mission.expire` `email.send` — the constants live next to the handler, so a later task adds a name without touching this one
- `singletonKey` convention = the aggregate id the job acts on (`feedback:<id>`), so a rescheduled timer replaces rather than duplicates
- cancellation is by singletonKey (e.g. a feedback settled before 72h cancels its auto-accept job); handlers must ALSO re-check state on run, because pg-boss cancellation is best-effort
- timers are scheduled in absolute time (`runAt`), never as "delay from now" computed at handler time ← clock drift across restarts

## result
- files: `apps/api/src/shared/application/{job-scheduler,index}.ts` · `apps/api/src/shared/infrastructure/jobs/{job-policy,job-registry,pg-boss-job-scheduler,pg-boss.service,jobs.module,index}.ts` + 3 unit tests + `jobs.int.test.ts` · `apps/api/src/shared/db/{transaction-scope,drizzle-transaction-manager}.ts` (refactor) + its tests · `apps/api/src/app.module.ts` · `packages/config/src/env.ts` (+`JOBS_ENABLED`) · `.env.example` · `scripts/docker-smoke.sh`
- verify: 197 tests pass (root 45 + web 30 + api unit 105 + api int 17) · `pnpm turbo run lint typecheck test build` 17/17 · `depcruise src` clean over 77 modules · coverage gate exits 0 · `pnpm test:docker` exits 0 and now also asserts `/ready` reports `"jobs":true`, so pg-boss starting is proven inside the real image
- **the transaction manager had to be rewritten to make this possible.** pg-boss joins a transaction through `ConnectionOptions.db.executeSql`, which needs the raw pg connection; Drizzle's `db.transaction()` never hands that out. `DrizzleTransactionManager` now checks a client out of the pool and drives `begin`/`commit`/`rollback` itself, and the ALS scope carries the Drizzle client **and** that same connection. T011's tests were rewritten against the new shape and its integration tests still pass unchanged
- **pg-boss is pinned to 11.1.2, not 12.** Version 12 is ESM-only, and a type-only import of an ESM package from this CommonJS app hits the same dead end T004 documented: tsc demands `resolution-mode` and Biome forbids the attribute. 11.1.2 is the last CommonJS major and carries everything needed here
- the retry and dead-letter policy lives on the **queue**, not on each send: v11 has `deadLetter` on `Queue` and not on `SendOptions`, which is the better place anyway — one policy per job name, applied once at boot. An int test reads `pgboss.queue` back and asserts the default arrived as `retry_limit` 3 with the right dead-letter name
- a handler may declare its own `retryPolicy` (a framework-free `{retryLimit, retryDelaySeconds, retryBackoff}`), which is what makes the dead-letter path provable in seconds rather than in a minute of exponential backoff
- pg-boss 11 has no lookup by singleton key, so `cancel` reads `pgboss.job` directly and then hands the ids to `boss.cancel`. The read is the only coupling and the state change still goes through pg-boss. `state` is the enum `pgboss.job_state`, so the predicate has to be `state::text = any($3::text[])` — without the cast PostgreSQL rejects the comparison outright
- workers attach in `onApplicationBootstrap`, not `onModuleInit`: Nest initialises a dependency's module first, so a context registering its handler in `onModuleInit` would otherwise be too late for the worker loop
- an unregistered job name fails at the **call site**, from `registry.require(name)` inside the send path, rather than when a worker eventually looks for a handler
- the integration tests prove the substance against a real database: a job enqueued in a rolled-back transaction leaves **no row at all** in `pgboss.job`, the same job in a committed transaction is delivered and the handler's write lands exactly once, handling the same payload twice reaches the same end state, cancelling by singleton key moves the job to `cancelled`, and a handler that always throws ends up in its dead-letter queue instead of retrying forever
- pg-boss owns the `pgboss` schema and creates it itself; drizzle's schema glob only covers `src/*/infrastructure/persistence/schema.ts`, so `drizzle-kit generate` never sees it
- `JOBS_ENABLED` is read with zod 4's `z.stringbool()`, so the string `"false"` really means false — `z.coerce.boolean()` would have made it true
- no SSOT divergence
