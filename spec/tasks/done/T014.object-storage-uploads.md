# T014 object storage & presigned uploads
> st:done@260907 | ssot:ARCH-37 ARCH-17 ARCH-41 ARCH-29 | base:ARCH@2 | dep:T006

## goal
S3-compatible storage behind a `FileStorage` port with browser-direct presigned uploads, so avatars and cover images never pass through the api.

## acceptance
- [v] `FileStorage` port: `createUploadUrl({ key, contentType, maxBytes })` → `{ url, fields?, publicUrl }`, `delete(key)`, `publicUrl(key)`; S3 adapter using `@aws-sdk/client-s3` + `@aws-sdk/s3-request-presigner` (works against both R2 and MinIO)
- [v] `minio` service added to `docker-compose.yml` with a bucket created at startup; config keys `S3_ENDPOINT` `S3_BUCKET` `S3_ACCESS_KEY_ID` `S3_SECRET_ACCESS_KEY` `S3_PUBLIC_BASE_URL`
- [v] `POST /api/v1/uploads` (authenticated once T019 lands; until then guarded by the throttler only) returns a presigned URL for a caller-declared purpose (`avatar` | `project-cover`) — the server derives the key, the client never proposes one
- [v] presign policy enforces content-type allowlist (image/png, image/jpeg, image/webp) and a 2MB cap; a mismatching upload is rejected by the storage service, not only by the UI
- [v] keys are `<purpose>/<uuidv7>.<ext>`; the api stores the key, never a full URL, and renders public URLs through `publicUrl(key)`
- [v] presign URLs expire in 5 minutes; the endpoint is rate limited per user/IP (ARCH-41)
- [v] deleting an entity that owns an image deletes its object best-effort in a job; a failed delete logs and does not fail the use case
- [v] test (int): presign against a MinIO Testcontainer, upload with the returned URL, read the object back; an upload with a disallowed content-type is refused by the server
- [v] test: an oversized declared `maxBytes` request is rejected with a 422 `{code}`; key generation never uses client input
- [v] test: `publicUrl` composes `S3_PUBLIC_BASE_URL` + key and is what the API returns to clients

## impl notes
- presigned PUT (single request) rather than POST policy forms ← simpler client, and R2 supports it identically to MinIO
- the api never proxies bytes (ARCH-37), so no multipart body parsing is configured on Fastify
- image processing (resize/optimize) is out of scope: v1 stores the original and the web layer sizes it with CSS; revisit if bandwidth becomes a problem
- MinIO in compose keeps local parity honest — the alternative (a filesystem adapter for dev) would let S3-only bugs reach production

## result
- files: `apps/api/src/shared/application/{file-storage,index}.ts` · `apps/api/src/shared/infrastructure/storage/{s3-file-storage,delete-object.job,storage.module,index}.ts` + `s3-file-storage.test.ts` `storage.int.test.ts` · `apps/api/src/uploads/**` (policy, use case, controller, module + 3 tests) · `packages/contracts/src/{uploads,index}.ts` + `uploads.test.ts` · `apps/api/src/openapi.ts` · `docker-compose.yml` (minio + bucket) · `packages/config/src/env.ts` · `.env.example` · `scripts/docker-smoke.sh` · committed `openapi.json` / `schema.d.ts`
- verify: 322 tests pass (root 63 + web 30 + api unit 194 + api int 35) · `pnpm turbo run lint typecheck test build` 19/19 · `depcruise src` clean · `pnpm api:contract:check` in sync · `pnpm biome format --write .` no-op · `pnpm test:docker` exits 0 with MinIO in the stack and a new check that `POST /api/v1/uploads` returns a signed URL
- **two real defects were found by uploading through a live MinIO**, and neither would have shown up in a mock. First, the SDK signs a checksum of the (empty) body at signing time, so every real upload through the URL would have failed to match — fixed with `requestChecksumCalculation: 'WHEN_REQUIRED'`. Second, `content-type` was **not** a signed header by default, so the allowlist was only advice: a caller could PUT `text/html` to a URL issued for a PNG. Both `content-type` and `content-length` are now in `signableHeaders`, and the integration tests prove MinIO answers **403** to a mismatching type and to a body larger than the signed length — refused by the storage service, not just the UI
- **the use case is a plain class with no framework import at all**, wired by a factory in `uploads.module.ts`. dependency-cruiser caught the first version importing `@nestjs/common` for `@Injectable`, which ARCH-11 forbids; this is now the pattern every use case follows, and it is what lets `create-upload-url.use-case.test.ts` use a hand-written fake with no test container
- the upload policy moved from `shared/infrastructure/storage` to `uploads/application`, where it belongs: an allowlist, a size cap and a key shape are application rules, not infrastructure
- keys are `<purpose>/<uuidv7>.<ext>` minted server-side from the declared content type. A test asserts two requests for the same purpose never produce the same key, and a contract test asserts a `key` a caller tries to pass in is simply dropped
- **restored a T006 guarantee that T012 had broken.** The OpenAPI generator called `app.init()`, which since T012 runs `onApplicationBootstrap` and starts pg-boss — so regenerating the contract needed a live database. It now creates the app with Nest's `preview: true`, which builds the module graph and registers routes without running any provider lifecycle. The document again generates with nothing reachable, and now carries `/api/v1/uploads` and its DTO schema
- MinIO's host ports are `${S3_PORT:-9000}` / `${S3_CONSOLE_PORT:-9001}`, because another project on this machine already holds 9000; the container-internal endpoint stays `http://minio:9000`, so only the host mapping moves
- `minio-bucket` is a one-shot `mc` container that creates the bucket and sets anonymous download, and `api` waits on it with `service_completed_successfully` — the same shape as the migration step
- deletion runs as the `storage.delete-object` job and swallows its own failure after logging: the row is already gone, so an orphaned object costs storage, never correctness
- image processing stays out of scope as the impl notes say; the api stores the original and the web sizes it
- no SSOT divergence
