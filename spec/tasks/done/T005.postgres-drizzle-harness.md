# T005 postgres, drizzle & integration test harness
> st:done@260907 | ssot:ARCH-13 ARCH-14 ARCH-21 ARCH-22 ARCH-29 ARCH-32 | base:ARCH@2 | dep:T003

## goal
Drizzle client + migration workflow against PostgreSQL 16, a docker-compose PG for local dev, and the Testcontainers harness every `*.int.test.ts` uses.

## acceptance
- [v] `docker-compose.yml` with a `pg` service (`postgres:16`), named volume, healthcheck, port from `.env`; `pnpm db:up` / `pnpm db:down` scripts
- [v] `src/shared/db`: a Nest `DbModule` providing the Drizzle node-postgres client under a `Symbol('DB')` token, pool sized from config, closed on shutdown
- [v] `drizzle.config.ts`: schema glob `apps/api/src/*/infrastructure/persistence/schema.ts`, `out: apps/api/drizzle`, dialect postgresql
- [v] `pnpm db:generate` writes migrations into `apps/api/drizzle/` (committed); `pnpm db:migrate` applies them — migrations are never applied on app boot (ARCH-13: applied on deploy)
- [v] `src/shared/db/columns.ts` helpers: `entityId()` (uuid pk, app-generated UUIDv7, no DB default) and `timestamps()` (`created_at`/`updated_at` timestamptz not null default now()) — every table in every later task uses them (ARCH-14)
- [v] `/ready` gains a `db` indicator running `select 1` with a 1s timeout → 503 when PG is down
- [v] Testcontainers harness: vitest `int` project matching `*.int.test.ts`, `globalSetup` starting one `postgres:16` container, running `db:migrate` against it and exporting `DATABASE_URL`; per-test isolation by truncating all non-migration tables in `beforeEach`
- [v] test: int test that connects through the DbModule, asserts `select 1`, and asserts the migration table exists
- [v] test: unit test that the `db` readiness indicator returns false (→ `/ready` 503) when the query rejects

## impl notes
- driver `pg` (node-postgres) + `drizzle-orm` — not postgres.js, since Testcontainers/pool teardown is the well-trodden path here and NestJS shutdown hooks need an explicit `pool.end()`
- one container for the whole int run (globalSetup), truncate-between-tests rather than a container per file ← container startup dominates otherwise; if a future suite needs isolation it can opt into its own container
- no schema tables are created in this task — the first real tables arrive with the AUTH context; the harness must therefore tolerate an empty `drizzle/` directory
- soft delete is NOT a global default (ARCH-14): the column helpers deliberately omit `deleted_at`
- compose here declares only `pg`; the `web`/`api` services are added by T010

## result
- files: `docker-compose.yml` · `apps/api/{drizzle.config.ts,vitest.int.config.ts,vitest.config.ts}` · `apps/api/drizzle/meta/_journal.json` · `apps/api/test-harness/{int-global-setup.ts,int-truncate.ts}` · `apps/api/src/shared/db/{db.token,db.module,create-pool,columns,db-readiness.indicator,index}.ts` + 5 tests · `apps/api/src/app.module.ts` · `packages/config/src/env.ts` (+`DATABASE_POOL_MAX`) · `.env.example` · root and api `package.json` scripts
- verify: 101 tests pass (root 23 + api unit 75 + api int 3) · `pnpm turbo run lint typecheck test build` 9/9 twice in a row · `depcruise src` clean · `pnpm biome format --write .` no-op · spec lint clean
- end-to-end against the compose database: `/ready` answers 200 `{"db":true}`, 503 `{"db":false}` while `pg` is stopped with `/health` still 200, and 200 again once `pg` is back — the pool recovers on its own
- **found and fixed a crash**: when PostgreSQL shuts down it pushes an error to its idle clients, and with no `pool.on('error')` listener Node turned that into an unhandled `'error'` event that killed the whole api process — so `/ready` could never have answered 503. `createPool` now logs and swallows it, and `create-pool.test.ts` proves the listener is there by emitting the event
- **found and fixed a flaky suite**: under the CPU contention of a parallel `turbo run`, the first `beforeEach` that boots a NestJS testing module exceeded vitest's 10s default `hookTimeout`. Reproduced deliberately with six busy loops, then fixed with `testTimeout: 30s` / `hookTimeout: 60s` in the api vitest config and re-verified five times under the identical load
- the int suite is a separate config (`vitest.int.config.ts`), not a project inside the unit config, because T003 established that plugins in a referenced vitest project are not applied and the swc transform is mandatory here. `api`'s `test` script runs unit then int so ARCH-24's `pnpm turbo run test` still covers both in one command — which does mean the standard test command now needs Docker
- `globalSetup` starts one `postgres:16` container, applies migrations with drizzle's programmatic `migrate()` (the same operation as `db:migrate`, without the CLI's env plumbing) and sets `DATABASE_URL` before any worker forks, so `@repo/config`'s import-time parse picks it up
- per-test truncation is scoped to the `public` schema, which excludes drizzle's `drizzle.__drizzle_migrations` bookkeeping by construction rather than by an exclusion list. `migrate()` creates that table even with zero migrations, so the int test can assert it
- `drizzle-kit` does not load the repo-root `.env`, so `db:generate` and `db:migrate` run as `node --env-file=../../.env node_modules/drizzle-kit/bin.cjs ...`; this keeps `@repo/config` the only reader of the environment (ARCH-31) with no extra dependency
- `db:generate` exits non-zero today with `No schema files found`, because no context owns a schema until T017. The pipeline was proven by generating against a throwaway `probe` schema: the emitted DDL was `id uuid PRIMARY KEY NOT NULL` with **no database default**, `created_at`/`updated_at timestamp with time zone DEFAULT now() NOT NULL`, and no `deleted_at` — exactly ARCH-14. The throwaway schema and its migration were then removed, and `columns.test.ts` now locks that shape in through drizzle's `getTableConfig`
- `.env.example` gained four compose-only keys (`POSTGRES_USER/PASSWORD/DB/PORT`) alongside the validated ones; the zod schema ignores unknown keys, so one `.env` serves both the app and docker-compose
- `DATABASE_POOL_MAX` extends the single env schema rather than adding a second one, as T002 requires
- no SSOT divergence
