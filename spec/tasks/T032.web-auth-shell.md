# T032 web: auth shell & sign-in
> st:todo | ssot:AUTH-1 AUTH-8 ARCH-5 ARCH-6 ARCH-7 ARCH-18 | base:AUTH@2 ARCH@2 | dep:T008 T019

## goal
Sign-in entry points, SSR-resolved session state, and the header auth slot the rest of the UI builds on.

## acceptance
- [ ] `entities/session` slice: an SSR loader reading `/auth/me` with the incoming cookie forwarded, exposing `useCurrentUser()` (null when signed out) — no client-side flash of the wrong state
- [ ] `features/auth` slice: `SignInDialog` with GitHub and Google buttons linking to `/api/v1/auth/:provider` with `returnTo` set to the current path; no email/password field anywhere (AUTH-1, AUTH-10)
- [ ] header auth slot (the placeholder from T007) renders avatar + menu (profile, settings, sign out) when signed in, otherwise the sign-in trigger
- [ ] sign-out posts to `/auth/logout` and clears the cached session query
- [ ] `?error=` on the landing route surfaces a human message per error code from the callback (T018), including the "provider has no verified email" case
- [ ] a route-level guard helper redirects signed-out users away from owner-only pages to sign-in with `returnTo`
- [ ] session state lives in TanStack Query, not Zustand ← it is server state (ARCH-7)
- [ ] test: render tests — signed-out header shows the sign-in trigger, signed-in shows the menu; each provider button targets the right URL with an encoded `returnTo`
- [ ] test: the error banner maps every callback error code and falls back for an unknown one
- [ ] test: the guard helper redirects when signed out and renders children when signed in

## impl notes
- the session query is prefetched during SSR so the first paint already knows who you are; the QueryClient-per-request rule from T008 is what makes that safe
- FSD placement: `entities/session` owns the query and types, `features/auth` owns the interactions, `widgets/header` composes them — no upward imports (ARCH-6)
- the sign-in trigger is a dialog rather than a route so `returnTo` is always the page you were on
