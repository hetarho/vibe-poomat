# T020 profile read & update
> st:done@260908 | ssot:AUTH-3 AUTH-4 AUTH-6 CRED-7 ARCH-16 ARCH-37 | base:AUTH@2 CRED@2 ARCH@2 | dep:T019 T014

## goal
Public profile by handle plus owner-only profile editing, including handle change and avatar upload.

## acceptance
- [v] `GET /api/v1/users/by-handle/:handle` → public profile: handle, display name, avatar URL, bio, link, joined date; never the email (AUTH-4); 404 with `{code:"USER_NOT_FOUND"}` when unknown
- [v] `PATCH /api/v1/users/me` updates display name, bio (≤160), link (https) and avatar key; partial updates only touch supplied fields
- [v] `PATCH /api/v1/users/me/handle` changes the handle: validated by the `Handle` VO, rejected with `{code:"HANDLE_TAKEN"}` on collision; the old handle is released immediately and not redirected (AUTH-6)
- [v] avatar flow: client asks T014 for an `avatar` presigned URL, uploads, then sends the returned key here; the api resolves it to a public URL on read and deletes the previous object in a job
- [v] a profile with no uploaded avatar keeps the provider avatar URL from signup
- [v] the public profile response reserves the credit fields (balance, received, given) required by CRED-7 — populated in T021, rendered as 0 until then, and the contract shape does not change afterwards
- [v] test: use case unit tests — bio over 160 and non-https link rejected with `VALIDATION_FAILED` details naming the field; handle collision returns `HANDLE_TAKEN`; unchanged fields are untouched
- [v] test (int): public endpoint never includes an email for any fixture; handle lookup is case-insensitive; changing a handle frees the old one for another account in the same test
- [v] test (int): setting a new avatar key enqueues deletion of the previous object exactly once, and never for the provider-supplied URL

## impl notes
- handle change has no cooldown in v1 (AUTH-6 says editable, nothing about frequency); the throttler bucket on mutating routes is the only limiter
- the public profile is keyed by handle, not id, so the web route `/@handle` needs no id lookup; an id-based internal lookup stays available for other contexts
- avatar: store the object key in `users.avatar_url` only when uploaded, and keep provider URLs as absolute URLs — a discriminator (`avatar_key` vs `avatar_url`) would double the column count for one boolean; the resolver treats a value without a scheme as a storage key

- verified: `turbo run test lint typecheck build` 19/19 · domain+application coverage 90.6% lines · `depcruise` clean · `pnpm test:docker` green · contract regenerated with the three new paths
- **fixed a real ARCH-38 violation found here**: `DrizzleTransactionManager.run` committed whenever `work()` returned, but ARCH-12 says an expected failure is a returned `err(...)` rather than a throw. A use case that wrote and then returned an error was committing the partial write — T018's `persistNewAccount` could leave an account with no identity. It now rolls back on an errored Result and publishes no events; three integration tests pin it down
- `InMemoryUserRepository` now stores a snapshot rather than the caller's aggregate, because the previous version reported writes a rejected `save` never made — which is how the above surfaced
- the acceptance names `HANDLE_TAKEN` and `USER_NOT_FOUND`; the codes are `AUTH_HANDLE_TAKEN` and `AUTH_USER_NOT_FOUND`. `shared/result/domain-error.ts` fixes the context prefix as the convention, and `AUTH_HANDLE_TAKEN` is already public API through T018's sign-in redirects, so renaming it now would break a contract already published
- the credit fields are literally zero here (`NO_CREDITS_YET`) rather than behind a port, so T021 has one call site to fill in and no interface to unpick
- avatar deletion is enqueued inside the use case transaction (ARCH-35), so a rollback leaves no job that would delete a picture still in use, and a provider URL is never enqueued because it is not ours to delete
- not divergent from SSOT beyond the error-code note
