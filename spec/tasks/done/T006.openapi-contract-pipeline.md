# T006 openapi contract pipeline
> st:done@260907 | ssot:ARCH-15 ARCH-16 ARCH-17 ARCH-4 | base:ARCH@2 | dep:T004

## goal
Shared zod contracts, an OpenAPI 3.1 document generated from Nest, and the typed `@repo/api-client` the web app consumes.

## acceptance
- [v] `packages/contracts`: zod schemas + inferred types exported per domain namespace; ships the cross-cutting ones now — `errorSchema` `{code, message, details?}`, `cursorPageSchema(item)` `{items, nextCursor}` (ARCH-17), and the primitives (`entityId`, `isoDate`)
- [v] api DTOs are built from contracts schemas via `nestjs-zod` `createZodDto`; a global `ZodValidationPipe` rejects bad input as 422 through T004's `ValidationError` shape (not nestjs-zod's default body)
- [v] `pnpm openapi:generate` builds the OpenAPI 3.1 JSON from a standalone Nest app (no listening server) into `packages/api-client/openapi.json`
- [v] `pnpm client:generate` runs `openapi-typescript` over that file into `packages/api-client/src/schema.d.ts`; both scripts chained as `pnpm api:contract`
- [v] `@repo/api-client` exports a configured `openapi-fetch` client factory: base URL argument, `credentials: 'include'`, and a response middleware turning any non-2xx `{code,message,details?}` body into a thrown typed `ApiError` (with `status`, `code`)
- [v] lint-stage check `pnpm api:contract && git diff --exit-code` fails when the committed openapi.json/schema.d.ts are stale
- [v] test: contract test that a DTO built from a contracts schema rejects a bad payload with 422 and the `{code:"VALIDATION_FAILED", details:[...]}` shape
- [v] test: unit tests for the api-client middleware — 404 body becomes `ApiError` with `code`, a 2xx body passes through typed, a non-JSON 500 becomes `ApiError{code:"INTERNAL"}`

## impl notes
- nestjs-zod version must be the zod-v4-compatible line (matches the T002 catalog pin); if it is not, the whole workspace stays on the zod version nestjs-zod supports — one zod in the tree is non-negotiable
- `@nestjs/swagger` + nestjs-zod's `patchNestJsSwagger()`/`zodToOpenAPI` path so schemas come from zod, never hand-written decorators (ARCH-16)
- web NEVER hand-writes API types (ARCH constraint): `@repo/api-client` is the only source; contracts is for schemas shared by both sides (form validation reuse), api-client for wire types
- error `details` for validation = zod flattened `fieldErrors`, so the web form layer can map them by field name
- generated files are committed (not gitignored) so `--filter=...[origin/main]` builds do not need a running Nest app

## result
- files: `packages/contracts/**` (common schemas + 10 tests) · `packages/api-client/**` (`api-error.ts`, `client.ts`, `index.ts`, 7 tests, committed `openapi.json` and `src/schema.d.ts`) · `apps/api/src/openapi.ts` · `apps/api/src/shared/presentation/{zod-validation.pipe.ts,presentation.module.ts,index.ts}` + `zod-validation.pipe.test.ts` · `biome.json` · root and api `package.json` scripts
- verify: 123 tests pass (root 40 + api unit 80 + api int 3) · `pnpm turbo run lint typecheck test build` 13/13 · `depcruise src` clean · `pnpm biome format --write .` no-op · spec lint clean · `pnpm api:contract:check` passes in sync and fails on a deliberately staled `openapi.json`
- versions resolved: `nestjs-zod@5.5.0` peers on `zod ^3.25.0 || ^4.0.0`, so the T002 catalog's zod 4.5.4 stands and there is exactly one zod in the tree. Its `@nestjs/swagger` peer range forces 11.x, which is what `setOpenAPIVersion('3.1.0')` needs for ARCH-16
- nestjs-zod 5.x has no `patchNestJsSwagger()`: `createZodDto` carries the OpenAPI metadata on the class itself and `cleanupOpenApiDoc(doc, { version: '3.1' })` post-processes what it produced. The generated document is OpenAPI 3.1.0 with a relative `/` server, so it is identical in every environment
- validation `details` is zod's flattened **`fieldErrors`** — an object keyed by field name — rather than the `[...]` array the acceptance sketched, because the impl notes call for exactly that and the web form layer needs to map messages onto inputs. Proven end to end: a bad payload answers 422 `{code:'VALIDATION_FAILED', message, details:{ownerId:[…],title:[…],tags:[…]}}`
- the generator (`src/openapi.ts`) creates the Nest app and calls `init()` without ever listening, then closes it. It runs as `nest build && node --env-file=../../.env.example dist/openapi.js`: the committed `.env.example` supplies a valid environment in CI with no `process.env` write anywhere in app source, keeping ARCH-31 intact
- **generated artifacts had to be excluded from Biome.** `biome check --write` reformatted `openapi.json` and `schema.d.ts`, and regeneration then unformatted them, so `api:contract:check` would have failed forever in a loop. Both paths are now in `biome.json`'s exclusions
- `@repo/api-client`'s build copies `src/schema.d.ts` into `dist/`, since tsc does not emit input declaration files and `dist/index.d.ts` refers to `./schema`
- `packages/contracts` deliberately has **no `test` script**: a bare `vitest run` inside a package walks up, finds the root config, and re-runs every project (it reported 33 tests for one file). Package tests belong to the root `unit` project; only apps own a runner, because only they need the swc transform
- `api:contract:check` exists as a root script but is not part of `turbo run lint` — regenerating the contract on every local lint is too slow. **T009 must call it in CI**, which is what the acceptance's "lint-stage check" asks for
- the document currently holds only `/health` and `/ready`, since no context owns an endpoint until T017. The DTO contract test defines its own controller in the test file rather than adding a production endpoint no SSOT asked for
- no SSOT divergence
