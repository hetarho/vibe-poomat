# T037 web: slot claim & report form
> st:todo | ssot:FDBK-1 FDBK-2 FDBK-3 FDBK-4 FDBK-10 ARCH-6 ARCH-7 | base:FDBK@2 ARCH@2 | dep:T035 T025 T026

## goal
Pressing Start to hold a slot, then the fixed-shape report form that submits it.

## acceptance
- [ ] Start button on a project with claimable slots: signed-out click opens sign-in with `returnTo`; owner never sees it; each rejection code renders its own message (`NO_SLOTS_AVAILABLE`, `ALREADY_CLAIMED`, `MISSION_NOT_OPEN`, `OWN_PROJECT`)
- [ ] an active hold shows the remaining time until `held_until` (24h, FDBK-1) and a "give up the slot" action
- [ ] the report form at `/missions/$id/report` renders exactly the FDBK-3 fields — first impression, where I got stuck, would I pay (yes/no + why), one suggestion, plus one input per mission question — each with a ≥20-character counter matching FDBK-10
- [ ] the mission task text and questions are shown alongside the form so the feedbacker can follow them, together with the live URL link
- [ ] a local draft is kept in `localStorage` per claim so a refresh does not lose the work; it is cleared on successful submit
- [ ] submit is blocked client-side until every field passes, and server `details` still map onto fields when they disagree
- [ ] after submit the form is replaced by a read-only view stating the report cannot be edited (FDBK-4) and that the maker has 72 hours
- [ ] an expired hold renders as expired with a path back to claim again if slots remain
- [ ] test: render tests — every FDBK-3 field present, a 19-character field blocks submit and names itself, all-valid enables it
- [ ] test: the countdown renders from `held_until` and the expired state replaces the form
- [ ] test: the draft survives a remount and is cleared after a successful submit
- [ ] test: each claim rejection code renders its distinct message

## impl notes
- FSD: `features/claim-slot`, `features/submit-feedback` over `entities/mission` and `entities/feedback`, page at `pages/report`
- the draft is per-claim `localStorage` (client-only convenience, never authoritative) — a server-side draft would contradict FDBK-4's single-shot submission
- the countdown is derived from the server's `held_until`; the client clock is only used for the ticking display, and expiry is always confirmed by the server's rejection
