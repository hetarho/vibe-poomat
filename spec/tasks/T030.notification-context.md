# T030 notification context: events, emails & preferences
> st:todo | ssot:NOTI-1 NOTI-2 NOTI-3 NOTI-4 NOTI-5 NOTI-6 NOTI-7 AUTH-4 ARCH-35 ARCH-36 | base:NOTI@2 AUTH@2 ARCH@2 | dep:T013 T027

## goal
Every domain event that moves the loop becomes one immediate email, honouring per-type opt-out and carrying a deep link and unsubscribe link.

## acceptance
- [ ] `apps/api/src/notification/` created with schema `notification_prefs(user_id uuid, type text, enabled boolean not null, updated_at, primary key(user_id, type))` — a missing row means enabled
- [ ] event → email handlers for every NOTI-2 type: `feedback_received` (maker) · `thread_reply` (other participant) · `feedback_accepted` / `feedback_rejected` (feedbacker) · `auto_accept_warning` (maker) · `auto_accepted` (both) · `mission_ended` (maker, with the refund summary)
- [ ] each handler resolves the recipient's provider email through the auth context's application service (AUTH-4) and enqueues `email.send`; nothing is sent inline (ARCH-36)
- [ ] one email per event, no batching or digesting (NOTI-1, NOTI-6)
- [ ] opt-out honoured per type; `auto_accept_warning` ignores the preference and always sends (NOTI-3)
- [ ] `GET/PATCH /api/v1/notifications/preferences` (owner only) reads and updates the toggles; the warning type is returned as always-on and rejects a disable attempt with 422
- [ ] every email body deep-links to the item and carries a per-type unsubscribe link; `GET /api/v1/notifications/unsubscribe?token=` disables that one type without a session — the token is an HMAC over `(userId, type)` with a config secret, constant-time compared (NOTI-4)
- [ ] a deleted account's pending email jobs resolve to no recipient and exit cleanly instead of failing
- [ ] React Email templates for all seven types in `packages/email`, each with subject, body copy, primary CTA and footer (sender per NOTI-5, "replies are not accepted")
- [ ] no in-app inbox, push or digest (NOTI-7)
- [ ] test: unit tests per handler — recipient resolution, opt-out respected, warning type sent even when disabled, deleted recipient short-circuits
- [ ] test: unsubscribe token round trip; a tampered token is refused; the link disables exactly one type
- [ ] test (int): a settle flow end to end enqueues exactly the expected email jobs (accept → feedbacker only; auto-accept → both), asserted against the console mailer
- [ ] test: template snapshots for all seven (subject line + CTA URL + unsubscribe URL present)

## impl notes
- the notification context subscribes to other contexts' domain events (ARCH-39) and owns no business rule beyond delivery ← keeps NOTI out of the settle transaction
- preference rows are created lazily on first opt-out; a missing row meaning "enabled" avoids backfilling every user on every new event type
- unsubscribe is a GET without a session (people click it from a mail client), so the token must be unguessable and single-purpose — it disables one type and can never enable, delete, or reveal anything
- `NOTIFICATION_SECRET` added to `@repo/config`; rotating it invalidates old unsubscribe links, which is acceptable and documented in `.env.example`
- copy lives in the templates, not the api ← NOTI-5's brand voice changes must not touch domain code
