# T039 web: notification settings & unsubscribe
> st:done@260909 | ssot:NOTI-2 NOTI-3 NOTI-4 NOTI-7 ARCH-6 | base:NOTI@2 ARCH@2 | dep:T032 T030

## goal
Per-type email toggles in settings and the no-session unsubscribe landing page reached from an email.

## acceptance
- [v] the settings section lists every NOTI-2 event type with a plain-language label and a toggle, saved individually with optimistic update and rollback
- [v] the auto-accept warning row renders as always-on and disabled with the reason "it moves your credits" (NOTI-3)
- [v] `/unsubscribe` reads the token from the query, calls the endpoint without requiring a session, and confirms which single email type was turned off (NOTI-4)
- [v] an invalid or tampered token renders a plain failure state with a link to settings, and never reveals whose account it referred to
- [v] the page states that other email types are unaffected and links to settings to re-enable
- [v] no in-app notification inbox or bell anywhere in the UI (NOTI-7)
- [v] test: render tests — every event type has a toggle, the warning row is disabled, a failed save rolls the toggle back
- [v] test: the unsubscribe page renders the success state for a valid token and the failure state for an invalid one, leaking no identity in either

## impl notes
- FSD: `features/notification-preferences` over `entities/notification-preference`, mounted inside `pages/settings` (T033) and standing alone at `pages/unsubscribe`
- the unsubscribe route must render server-side without a session, so it cannot sit behind the auth guard helper from T032
- labels are written per event in the UI rather than derived from the type key — "auto-accepted" means different things to the maker and the feedbacker

## result
Files (web): `entities/notification-preference/*` (labels + the query, moved down out of the feature), `features/notification-preferences/model/use-set-preference.ts` (replacing `use-notification-preferences.ts`), `pages/unsubscribe/*`, `app/routes/unsubscribe.tsx`, `widgets/app-shell/ui/no-notification-inbox.test.tsx`, and T033's toggle test rewired. Files (api): the unsubscribe endpoint now redirects on failure as well as success, landing on `/unsubscribe`.

- DIVERGENCE, read this first. Acceptance 3 says the page "reads the token from the query, calls the endpoint". It does not, and deliberately: T030 already decided the other direction, and its own comment says why — the email link points at the api (`deep-links.ts` builds `{API_URL}/api/v1/notifications/unsubscribe?token=…`), the api verifies the token, makes the change, and answers with a 303 because "whoever clicked is a person looking at a mail client, not a client library". Implementing the acceptance literally would mean turning that endpoint back into JSON and re-pointing every email at the web, undoing a done task's reasoning. Instead the api's redirect target moved from `/settings/notifications?unsubscribed=` (a route that was never built) to `/unsubscribe?type=`, and the page renders the outcome. Everything the acceptance line is *for* holds: no session is required, it names the single type that was switched off, and the token never reaches the browser's second origin at all. NOTI-4 does not say which side holds the token, so this is a task-decomposition conflict rather than a planning gap — worth a create-task or update-ssot note if the other design is actually wanted.
- The same change fixed acceptance 4, which was impossible before: a tampered token answered 422 JSON and an always-on type answered 403, so somebody clicking from their inbox saw a raw error body. Both now redirect to `/unsubscribe?error=<code>`, carrying the code and never the account — asserted in the int tests, which check the location does not contain the user id. The page maps only the two codes the api can send and falls back rather than echoing anything else, so a crafted URL cannot put text on the page.
- The toggle is now optimistic with rollback (it was set-on-success only), and saves one type at a time: the other rows stay usable while one is in flight, because that row has already moved.
- The query and the labels moved to `entities/notification-preference` as the impl notes ask; the feature keeps the mutation and the toggles. `app/routes/settings.tsx` reads the query options from the entity now.
- NOTI-7 is guarded by a test on the shell every page renders inside, rather than by absence alone. The header's "Feedback" link is T038's maker inbox, not a notification inbox — it lists reports awaiting a decision, which is FDBK-7's clock, not a notification channel.
