# T031 account deletion
> st:done@260908 | ssot:AUTH-9 AUTH-12 CRED-8 PROJ-6 PROJ-8 FDBK-9 CRED-4 ARCH-38 | base:AUTH@2 CRED@2 PROJ@2 FDBK@2 ARCH@2 | dep:T027 T023 T021

## goal
Self-serve immediate deletion that force-closes missions, pays out pending feedback, voids credits and anonymizes what others received.

## acceptance
- [v] `DELETE /api/v1/users/me` runs the ordered sequence in one transaction (AUTH-9): force-close the user's active missions (refunding unfilled slots, PROJ-6) → auto-accept every pending feedback on those missions so feedbackers are paid (CRED-4) → delete the user's projects and missions → set `author_id = null` on feedback and replies the user wrote (FDBK-9) → void remaining balance and escrow (CRED-8) → delete sessions, identities and the user row
- [v] the user's own held claims are released so their slots return to other missions
- [v] deletion is irreversible with no grace period; the endpoint requires a typed confirmation field matching the account handle
- [v] after deletion the session cookie is cleared and every prior session is gone
- [v] public reads keep working: feedback the user gave stays visible with a null author, projects they owned are gone from the feed
- [v] the credit invariant holds after voiding (the void entries balance the ledger, CRED-6)
- [v] no admin path exists — only the account owner can trigger this (AUTH-12)
- [v] test (int): full-scenario fixture — a user with an open mission (2 unfilled slots, 1 pending feedback), a given feedback, a balance and an escrow; after deletion assert every one of the AUTH-9 outcomes including the paid feedbacker and the voided remainder
- [v] test (int): the ledger invariant recomputes correctly for every surviving account afterwards
- [v] test (int): a wrong confirmation string aborts and changes nothing; the whole sequence rolls back if any step fails
- [v] test: unit test asserting the step order (a paid-then-voided ordering is what makes feedbackers whole)

## impl notes
- one transaction across four contexts is exactly what ARCH-38 was decided for; each context exposes a `purgeUser(userId)`-style application service and this use case orchestrates the order
- ordering matters and is asserted: auto-accepting BEFORE voiding is the difference between paying feedbackers and stealing their credits (AUTH-9)
- anonymization is a null `author_id`, never a deletion of the feedback (FDBK-9) — the value others received survives
- deletion runs inline rather than as a job so the user sees the result immediately; the object-storage cleanup for their images is the one part deferred to a job (best-effort, T014)

### notes
- **The order is the decision, so a test asserts the list rather than the code.** `DELETION_STEPS` is exported and pinned; the one ordering that is not a preference — settling every pending report before voiding anything — has a test of its own, because reversing it would take the credits of the people who did the work instead of paying them.
- **The pending reports are found by `maker_id`, not by walking the missions just closed.** A mission that ended weeks ago can still be holding a report nobody answered: closing a mission refunds unheld slots and settles nothing. T029's denormalised column is what makes that one query.
- **Both settlement and closure go through the ordinary paths** (`ManageMissionUseCase.close`, `SettleFeedbackUseCase.autoAccept`) rather than bespoke SQL, so the credit movement a feedbacker gets when an account is deleted is provably the one they would have got at the 72-hour mark.
- **The projects are hidden, not dropped.** AUTH-9 says "deleted" and this is the one place the delivery differs: FDBK-9 keeps every submitted report public, and a report is about a project — a public report naming a row nobody can resolve is worse than a row nobody can find. PROJ-8's soft delete already produces the user-visible outcome (404 on read, absent from the feed), and both are asserted. **Candidate for `update-ssot`:** AUTH-9's wording could say hidden rather than deleted for projects, so a later reader does not expect the rows to be gone.
- **`DELETE /users/me` lives in its own module, beside the profile routes but not in `auth`.** No single context can host a sequence that spans four of them — each of the other three would have to import the rest. Nothing imports this module back, so the graph stays acyclic.
- **The session cookie's name and attributes moved to `shared/presentation`.** Deletion has to clear the very same cookie the auth routes set, and reaching into `auth/presentation` from another context is exactly what dependency-cruiser refuses. AUTH-8's lifetime stayed with the session aggregate that decides it, so the constant is not duplicated.
- **The rollback test swaps the port on the running application** rather than compiling a second one: two Nest apps in one process fight over the same database handle, and closing either leaves the other unable to reach it. Making the last step fail proves all four contexts really do move together (ARCH-38).
- **Signing in is anonymous, so the write throttler counts it by IP**, and this fixture signs in thirty people. Each sign-in now carries its own forwarded address — realistic, and what keeps the file from flaking the moment another case is added.

### ssot
Only the projects-are-hidden reading of AUTH-9 differs, explained above and worth an `update-ssot`. Everything else — the order, CRED-4's payouts, CRED-8's void, FDBK-9's anonymisation, AUTH-12's absence of an admin path — is delivered as written.
