# T025 feedback slots: claim & release
> st:todo | ssot:FDBK-1 FDBK-2 PROJ-4 ARCH-35 ARCH-38 | base:FDBK@2 PROJ@2 ARCH@2 | dep:T023 T012

## goal
Pressing Start holds one slot for 24 hours, with automatic release and the one-slot-per-account-per-mission rule.

## acceptance
- [ ] `apps/api/src/feedback/` created with schema
      `feedback_claims(id uuid pk, mission_id uuid not null, user_id uuid not null, state text not null, held_until timestamptz not null, released_at timestamptz, created_at, updated_at, index(mission_id), unique(mission_id, user_id) where state in ('held','submitted','settled'))`
- [ ] `POST /api/v1/missions/:id/claims` holds a slot for 24h (FDBK-1) when: signed in, mission open, caller is not the project owner, caller has no live claim on this mission, a claimable slot remains (FDBK-2)
- [ ] rejections carry distinct codes: `MISSION_NOT_OPEN` `OWN_PROJECT` `ALREADY_CLAIMED` `NO_SLOTS_AVAILABLE`
- [ ] `DELETE /api/v1/claims/:id` lets the holder give the slot back before submitting
- [ ] `slot.release` job scheduled at `held_until` releases a still-held claim (state `released`), freeing the slot; cancelled on submit or manual release; re-running it is a no-op
- [ ] a released claim does not block re-claiming — no re-claim limit in v1 (FDBK-1)
- [ ] `ClaimHeld` / `ClaimReleased` events emitted for mission slot accounting (T023)
- [ ] application service `countLiveClaims(missionIds)` used by T023/T024 for claimable-slot math, batched
- [ ] test: unit tests for every rejection branch with in-memory repositories
- [ ] test (int): the partial unique index blocks a second live claim by the same user while allowing a new claim after release; two concurrent claims for the last slot leave exactly one held
- [ ] test (int): the release job frees the slot at `held_until`, is idempotent, and is cancelled by a submit

## impl notes
- one claim row per hold (rather than N pre-created slot rows per mission) ← slots are a count on the mission; materializing them would double the state to keep consistent, and the partial unique index already enforces FDBK-2
- `held_until` is absolute (opened at + 24h) and the job is scheduled with `runAt` (ARCH-35 note on clock drift)
- the "claimable" number is derived: `mission.slots − count(state in held|submitted|settled)`; nothing caches it
- the owner check reads the project through the project context's application service, not a join (ARCH-14)
