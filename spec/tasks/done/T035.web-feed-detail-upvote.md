# T035 web: feed, project detail & upvote
> st:done@260908 | ssot:PROJ-9 PROJ-10 PROJ-11 PROJ-1 ARCH-6 ARCH-7 | base:PROJ@2 ARCH@2 | dep:T032 T024

## goal
The landing feed with tag filter, the popular tab, and the project detail page with upvoting.

## acceptance
- [v] `/` renders the default feed (projects with open slots first, then newest — PROJ-9) as cards: cover, title, pitch, tags, owner, upvote count, claimable-slot badge; infinite scroll on the cursor
- [v] tag filter chips update the URL query and the SSR loader honours it on a cold load
- [v] `/popular` renders the 7-day ranking (PROJ-10) with the same card component
- [v] `/projects/$id` renders the full project (description markdown, live URL as a prominent external link with `rel="noopener noreferrer"`), the owner block, the active mission summary, and the public feedback list
- [v] upvote button toggles optimistically with rollback on error; hidden (not merely disabled) on your own project; a signed-out click opens the sign-in dialog with `returnTo` (PROJ-11)
- [v] a soft-deleted project renders 404 for visitors and an "archived" banner for its owner (PROJ-8)
- [v] empty states for both tabs and for a project with no feedback yet
- [v] test: render tests — card shows the slot badge only when slots are claimable; own-project card hides the upvote control
- [v] test: optimistic upvote increments then rolls back on a failed mutation; the count matches the server value afterwards
- [v] test: signed-out upvote opens the sign-in dialog and does not call the API
- [v] test: tag filter reflects into the URL and back on reload

## impl notes
- FSD: `pages/feed`, `pages/popular`, `pages/project-detail` over `widgets/project-card`, `features/upvote-project`, `entities/project` — the card widget is shared by all three so ranking changes never fork the markup
- infinite scroll uses `useInfiniteQuery` with the opaque cursor from T024; page state stays in the query cache, not Zustand (ARCH-7)
- the live URL opens in a new tab: the whole point of PROJ-2 is that a feedbacker can actually use the thing

## result
Files (web): `entities/project/{model/feed.query.ts,lib/feed-search.ts+test}`, `entities/feedback/*` (project feedback query, `FeedbackSummary`), `features/upvote-project/*`, `widgets/project-card/*`, `widgets/project-feed/*`, `pages/{feed,popular,project-detail}/*`, `app/routes/{index,popular,projects.$id}.tsx`; `shared/ui/user-avatar.tsx` (moved out of `entities/session`); `pages/home` deleted, its heading now leads the feed. Files (api): `GET /projects/:projectId/feedbacks` (repository `listForProject`, `ReadFeedbackUseCase.forProject`, int tests) and `upvotedByViewer` on the project read.

- Two api gaps had to be closed, the same kind T033 hit. (1) There was no way to list a project's public feedback: only `GET /missions/:id/feedbacks` existed, and the project response carries only the mission that is still open (PROJ-5), so feedback from an ended mission was unreachable — FDBK-9 makes all of it public. Added `GET /projects/:projectId/feedbacks`, cursor-paged like the profile list, walking the `feedbacks_project_idx` that already existed. (2) `projects.Project` had `upvoteCount` but not `upvotedByViewer`, so the detail page could not render PROJ-11's toggle state; added it, resolved through the upvote port for a signed-in reader exactly as the feed card already did.
- `widgets/project-feed` takes `renderCard` rather than importing `widgets/project-card`: FSD forbids one widget reaching into another, so the two tabs (which differ only in the sort) share the paging and the chips and each hands in the same card.
- `UserAvatar` moved from `entities/session` to `shared/ui`: `entities/feedback` needs it for a report's author, and entity-to-entity imports are forbidden. It never depended on the session — only on a name and a picture.
- The feed loaders use `prefetchInfiniteQuery`, not `ensure`: an `ensure` rethrows, and `/` is public, so a briefly unreachable api would blank the landing page. The project detail still ensures — without the project there is no page.
- PROJ-3's filter is parsed in `entities/project/lib/feed-search.ts` (`parseFeedSearch`/`feedSearchFor`), shared by both routes, so the URL contract is tested once rather than duplicated in two route files.
- The upvote control is decided in three ways by whoever composes it (the card and the detail page): nothing at all for the owner (PROJ-11 hides rather than disables), a `SignInDialog`-wrapped `UpvoteControl` for a signed-out reader, the real `UpvoteButton` otherwise. The presentational control and the mutating button are separate exports so the dialog can trigger on one without the other's hook running.
