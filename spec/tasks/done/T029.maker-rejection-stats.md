# T029 maker rejection stats
> st:done@260908 | ssot:FDBK-8 FDBK-6 CRED-7 AUTH-7 | base:FDBK@2 CRED@2 AUTH@2 | dep:T027

## goal
Public rejection rate and reason distribution on a maker's profile — the only check on maker power in v1.

## acceptance
- [v] application service `getMakerStats(userId)` -> `{ settledCount, rejectedCount, rejectionRate, reasons: { task_not_done, no_substance, spam_abuse } }` computed over feedback on projects the user owns
- [v] auto-accepted reports count as accepted (they were never rejected) and pending ones are excluded from both numerator and denominator
- [v] the profile response (T020) carries the stats block; `rejectionRate` is null when `settledCount` is 0 so the UI can say "no history yet" instead of showing 0%
- [v] exposed publicly (FDBK-8) with no role gating (AUTH-7)
- [v] the query is a single grouped aggregate over `feedbacks` by owner, using the denormalized `project_id`->owner lookup, and is covered by an index that keeps it out of a sequential scan
- [v] test: unit tests over a fixture set — mixed accepted/rejected/auto-accepted/pending produce the documented rate and per-reason counts; a maker with no settled feedback yields null
- [v] test (int): the aggregate matches a naive recount over the same rows, and the profile endpoint returns the block

## impl notes
- computed on read rather than maintained as counters <- volumes are tiny in v1 and a stale counter on a public trust signal is worse than a slightly slower profile query
- the denominator is settled feedback, not submissions: a maker cannot lower their rate by leaving reports pending, because pending ones auto-accept at 72h anyway (FDBK-7)
- no time window: FDBK-8 does not define one, and a lifetime rate is the harsher, simpler signal

### notes
- **The owner is denormalised onto the row, not looked up through the project.** The acceptance describes reaching the owner via `project_id`, which in SQL means joining `feedbacks` to `projects` — a cross-context join, and the codebase already refuses those: `SLOT_OCCUPANCY_READER` exists precisely so the project context never joins `feedback_claims`. So `maker_id` is written onto the report at submit time from the value the mission port already hands over, and the aggregate reads `feedbacks` alone. This makes the acceptance's own first clause — *a single grouped aggregate over `feedbacks`* — literally true, and PROJ-12 gives a project one owner for life, so the copy cannot go stale. An int test asserts `maker_id` equals `projects.owner_id` for every row.
- **The service method is `statsFor`, not `getMakerStats`.** It implements `MakerStatsReader`, so the port's name wins; the class is still `GetMakerStatsUseCase`.
- **`ClaimStoreModule` moved into its own file.** `AuthModule` now needs it, and `feedback.module.ts` imports `auth.module.ts` — importing the module from where it was would have been a file cycle. In its own file it depends on nothing in `auth`, so `AuthModule` can name what it uses instead of relying on `@Global()` to happen to have registered it. That reliance is what made four int tests fail to build a graph.
- **An unattributable rejection counts in the rate but in no category.** No such row can exist today (`rejection_reason` is always set on a rejection), but the arithmetic must not invent a category if one ever appears; a unit test pins it.
- **The migration backfills before it constrains** — add nullable, fill from `projects`, then `SET NOT NULL` — because a plain `NOT NULL` add fails against any database already holding reports. That `UPDATE ... FROM projects` is the one place the two tables meet, and a migration is schema, not a query the context runs.
- **Every credit in the int test moves through the real ledger**, so each maker's outcomes stay inside the two credits CRED-1 seeds: a rejection refunds and can be spent again, an acceptance and a pending report cannot. A `pending` outcome also has to come last for a maker, because the mission behind it stays open and PROJ-5 allows a project only one of those.
