# T027 feedback settle: accept, reject, auto-accept
> st:todo | ssot:FDBK-6 FDBK-7 CRED-4 PROJ-6 ARCH-35 ARCH-38 ARCH-39 | base:FDBK@2 CRED@2 PROJ@2 ARCH@2 | dep:T026 T021 T012

## goal
The maker's accept/reject decision, the 48h warning and 72h auto-accept timers, and the credit movements each produces.

## acceptance
- [ ] `POST /api/v1/feedbacks/:id/accept` (project owner only, state `pending`) → state `accepted`, 1 credit moves from mission escrow to the feedbacker (CRED-4), `SlotSettled` emitted
- [ ] `POST /api/v1/feedbacks/:id/reject` requires a reason from the fixed set `task_not_done` `no_substance` `spam_abuse` plus an optional note; → state `rejected`, 1 credit returns from escrow to the maker's balance (FDBK-6, CRED-4); reason and note are visible to the feedbacker and public with the report (FDBK-9)
- [ ] `feedback.auto-accept` job at +72h settles a still-pending report exactly as an accept and marks it auto-accepted, distinguishable in the response (FDBK-7)
- [ ] `feedback.warn` job at +48h emits `AutoAcceptWarning { feedbackId, makerId }` for NOTI (T030) only when the report is still pending
- [ ] settling cancels the remaining timers and is idempotent: a second settle attempt on a non-pending report returns 409 `{code:"FEEDBACK_ALREADY_SETTLED"}` and moves no credits
- [ ] when the settled slot was the mission's last outstanding one, `SlotSettled` drives the mission to `completed` (T023)
- [ ] the whole settle runs in one transaction across feedback + credit + mission state (ARCH-38); the notification effects are jobs enqueued in it (ARCH-39)
- [ ] test: unit tests — non-owner rejected, unknown reason rejected, note optional, double settle blocked, exact credit calls asserted per branch
- [ ] test (int): accept moves exactly 1 credit escrow→feedbacker and the ledger invariant still holds; reject moves it escrow→maker
- [ ] test (int): the auto-accept job at 72h pays the feedbacker and is a no-op when the report was already settled; running it twice pays once
- [ ] test (int): the warn job fires only for still-pending reports; settling before 48h cancels both jobs

## impl notes
- auto-accept reuses the accept use case with an `actor: 'system'` flag rather than a parallel code path ← the credit movement must be provably identical
- idempotence is enforced by the state check inside the transaction plus the credit ledger's `(type, account, ref)` unique key, so even a duplicated job cannot double-pay
- rejection reasons are a domain enum shared through `packages/contracts` so the web radio group and the profile stats (T029) use one list
- the maker cannot reject after 72h — the auto-accept has already settled it; the 409 above is the honest answer rather than a silent no-op
