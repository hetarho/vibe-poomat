# T028 feedback thread
> st:done@260908 | ssot:FDBK-5 FDBK-9 AUTH-9 ARCH-17 | base:FDBK@2 AUTH@2 ARCH@2 | dep:T026

## goal
A public-readable reply thread on each feedback where only the maker and the feedbacker can post.

## acceptance
- [v] schema `feedback_replies(id uuid pk, feedback_id uuid not null, author_id uuid, body text not null, created_at, index(feedback_id, created_at))`
- [v] `POST /api/v1/feedbacks/:id/replies` — allowed only for the project owner and the report author (FDBK-5); anyone else gets 403 `{code:"NOT_A_THREAD_PARTICIPANT"}`
- [v] body required, 1-2000 characters after trimming
- [v] `GET /api/v1/feedbacks/:id/replies` is public with cursor pagination, oldest first; a reply from a deleted account shows a null author (AUTH-9)
- [v] replies are allowed at any time after submit, including after the feedback is settled (FDBK-5 sets no window)
- [v] each posted reply emits `ThreadReplied { feedbackId, authorId, recipientId }` for NOTI (T030) — the recipient is the other participant
- [v] replies are immutable: no edit or delete endpoint in v1
- [v] test: unit tests — a third party is refused, empty/oversized bodies rejected, the recipient in the event is always the other participant
- [v] test (int): both participants can post, ordering and cursor paging are stable, a null author renders as deleted-user data
- [v] test (int): posting on a settled feedback still works and still emits the event

## impl notes
- participants are resolved per request from the feedback row (`author_id`) and the project owner; there is no participants table ← the pair is fixed for the life of the thread
- `author_id` nullable for the same reason as the report (AUTH-9 anonymization)
- no read-receipts, reactions or nesting: FDBK-5 describes a flat two-party thread

### notes
- **The keyset walks the indexed columns, not the id.** The first version paged on `id > cursor` — correct, because a UUIDv7 sorts by the instant it was minted, but it left `feedback_replies_thread_idx (feedback_id, created_at)` unusable for the ordering, so the index this task mandates would have been decoration. The query now compares the row `(created_at, id) > (…)` and orders by the same pair, which the index positions directly; the id stays as the tiebreaker so two replies in one millisecond still have a total order. The cursor carries both keys, opaquely (ARCH-17).
- **`author_id` has no foreign key**, matching the report row: AUTH-9 nulls it rather than deleting the reply, and an int test pins that a nulled author still renders the message with `author: null`.
- **A settled report is still a thread.** FDBK-5 sets no window, so `reply` never looks at the feedback's state — the conversation about a rejection is the one worth having. Pinned by an int test that rejects first and then posts.
- **The recipient is computed, never stored.** It is whichever participant the author is not, derived per request from the feedback's `author_id` and the mission owner. A reply where the other side is already anonymised (AUTH-9) is refused rather than announced to nobody.
- **No edit or delete route exists**, and an int test asserts PATCH/PUT/DELETE on a reply are all 404 — otherwise "v1 has no edit" is a claim nothing checks.
