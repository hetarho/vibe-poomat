## impl notes
- session id = 32 random bytes base64url, generated in the domain via a `SessionIdGenerator` port so tests are deterministic (ARCH-18: opaque 256-bit)
- sessions are stored hashed? No — the cookie value IS the primary key: it is high-entropy, single-purpose and rotated on sign-in; hashing would only help against a DB read that already exposes everything else
- `citext` for handle rather than a lower() functional index ← handle equality is used in many places (routes, mentions later) and one column type keeps every query honest
- no `deleted_at` on users: AUTH-9 deletes the row outright (T031); other contexts hold `user_id` values that become dangling and render as "deleted user", which is exactly what ARCH-14's no-cross-context-FK rule allows
- reserved handles: `admin api me settings login logout signin signup new about help support` — kept as a constant list in the domain, not a table
- no `AccountCreated` emission here; the signup use case (T018) owns it

- fixed while writing the int test: `isUniqueViolation` only saw the bare driver error, but Drizzle 0.45 reports a failed statement as its own error and keeps the pg one as `cause` — a duplicate handle was escaping as a driver exception instead of `AUTH_HANDLE_TAKEN`. It now walks the cause chain, with a unit test for both shapes
- `Session` deliberately does not extend the shared `Entity`: its identity is the opaque cookie value, not an `EntityId`, and the base class exists to give UUID-identified rows their equality

- display name is capped at 50 code points and the avatar url must be an absolute http(s) URL. Neither limit is fixed by AUTH-3, and `display_name text not null` would otherwise be unbounded; update-ssot should pin them if 50 is the wrong number
- deployment note: `CREATE EXTENSION citext` needs rights the application role may not hold on a managed PostgreSQL. The extension has to exist before this migration runs there
