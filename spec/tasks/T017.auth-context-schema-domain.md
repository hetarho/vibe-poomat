## goal
The `auth` bounded context: users, provider identities and sessions as schema, domain model and Drizzle repositories.

## acceptance

- [ ] schema in `auth/infrastructure/persistence/schema.ts`:
      `users(id uuid pk, handle citext unique not null, display_name text not null, avatar_url text, bio varchar(160), link text, created_at, updated_at)`
      `identities(id uuid pk, user_id uuid not null, provider text not null, provider_user_id text not null, email text not null, email_verified boolean not null, created_at, updated_at, unique(provider, provider_user_id), index(email) where email_verified)`

- [ ] migration generated and committed; `citext` extension enabled by the migration
- [ ] domain: `User` aggregate (profile fields + `rename`, `changeHandle`, `updateProfile` invariants), `Handle` VO (3-20 chars `^[a-z0-9_]+$`, lowercased, reserved-word list rejected), `Bio` VO (≤160), `ExternalLink` VO (https URL), `ProviderIdentity` entity, `Session` entity (opaque id, sliding expiry)
- [ ] `Session.touch(now)` extends `expires_at` to `now + 30d` (AUTH-8) and is a no-op when the last touch was under an hour ago
- [ ] repository interfaces in `domain` (`UserRepository`, `IdentityRepository`, `SessionRepository`) with Drizzle adapters in `infrastructure`, registered under Symbol tokens
- [ ] `IdentityRepository.findByVerifiedEmail(email)` and `findByProviderId(provider, id)` exist — the two lookups AUTH-5 needs
- [ ] `UserRepository.generateAvailableHandle(base)` applies the numeric-suffix collision rule (AUTH-6)
- [ ] test: VO unit tests (handle charset/length/reserved, bio limit, link must be https), `Session.touch` sliding + throttled-write rule, `User.changeHandle` invariants
- [ ] test (int): unique constraints hold (same provider+provider_user_id twice fails, duplicate handle fails case-insensitively); `findByVerifiedEmail` ignores unverified rows; handle generation resolves collisions

## impl notes
- session id = 32 random bytes base64url, generated in the domain via a `SessionIdGenerator` port so tests are deterministic (ARCH-18: opaque 256-bit)
- sessions are stored hashed? No — the cookie value IS the primary key: it is high-entropy, single-purpose and rotated on sign-in; hashing would only help against a DB read that already exposes everything else
- `citext` for handle rather than a lower() functional index ← handle equality is used in many places (routes, mentions later) and one column type keeps every query honest
- no `deleted_at` on users: AUTH-9 deletes the row outright (T031); other contexts hold `user_id` values that become dangling and render as "deleted user", which is exactly what ARCH-14's no-cross-context-FK rule allows
- reserved handles: `admin api me settings login logout signin signup new about help support` — kept as a constant list in the domain, not a table
- no `AccountCreated` emission here; the signup use case (T018) owns it
