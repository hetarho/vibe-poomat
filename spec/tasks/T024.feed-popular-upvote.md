# T024 feed, popular & upvote
> st:todo | ssot:PROJ-9 PROJ-10 PROJ-11 PROJ-3 ARCH-17 ARCH-33 | base:PROJ@2 ARCH@2 | dep:T022

## goal
The default feed (open slots first), the 7-day popular tab, and one-per-account project upvotes.

## acceptance
- [ ] schema `upvotes(project_id uuid, user_id uuid, created_at, primary key(project_id, user_id), index(project_id, created_at desc))`
- [ ] `GET /api/v1/projects` default feed: projects with claimable slots first ordered by mission opened_at desc, then the rest by created_at desc; cursor pagination (ARCH-17); optional `tag` filter; soft-deleted projects excluded (PROJ-9)
- [ ] `GET /api/v1/projects?sort=popular` orders by upvotes in the last 7 days desc, ties broken by total upvotes desc, then created_at desc (PROJ-10)
- [ ] `POST /api/v1/projects/:id/upvote` toggles: creates or deletes the row and adjusts `projects.upvote_count` in the same transaction; upvoting your own project → 403 `{code:"CANNOT_UPVOTE_OWN_PROJECT"}` (PROJ-11)
- [ ] each list item carries what a card renders: title, pitch, tags, cover URL, owner handle/avatar, upvote count, whether the caller upvoted, claimable slot count
- [ ] the cursor is opaque and stable under concurrent inserts (encodes the sort keys + id, not an offset)
- [ ] no server-side cache (ARCH-33): correctness comes from indexes, not memoization
- [ ] test: unit test of the cursor encode/decode round trip including the popular tab's composite key
- [ ] test (int): feed ordering fixture — a project with claimable slots outranks a newer one without; tag filter narrows correctly; a soft-deleted project never appears
- [ ] test (int): popular window — an upvote 8 days old does not count, one 6 days old does; ties fall back to total then recency
- [ ] test (int): toggling twice returns to the original state and `upvote_count` matches `count(*)`; own-project upvote rejected; the same user upvoting twice concurrently ends with one row

## impl notes
- "projects with open slots first" is expressed as a computed rank column in one query (`case when claimable > 0 then 0 else 1 end`) rather than two queries stitched in application code ← pagination across a UNION is where this design usually breaks
- the 7-day popular count is computed with an index-only scan over `upvotes(project_id, created_at)`; if that ever gets slow the fix is a materialized rollup, not a cache (ARCH-33)
- claimable slot count per project comes from the feedback context's application service in one batched call per page, not per row (N+1)
- `upvote_count` is maintained transactionally instead of triggered ← the trigger would be invisible to the domain model and untestable in unit tests
