# T002 env config package
> st:done@260907 | ssot:ARCH-31 ARCH-15 ARCH-2 | base:ARCH@2 | dep:T001

## goal
One zod-validated env module (`@repo/config`) that is the only place in the repo reading `process.env`.

## acceptance
- [v] `packages/config` parses and freezes env once at module load and exports the typed `env` object plus the `envSchema`
- [v] base keys: `NODE_ENV` (development|test|production) · `LOG_LEVEL` (default info) · `API_PORT` (number, default 3001) · `API_URL` · `WEB_URL` · `DATABASE_URL` (postgres URL) — later tasks extend the same schema, never a second one
- [v] invalid/missing env throws once at boot with every offending key listed in the message (not one-by-one)
- [v] `.env.example` committed with every key and a safe placeholder value; `.env` gitignored
- [v] test: valid env parses to the typed object; missing `DATABASE_URL` throws a message naming `DATABASE_URL`; a non-numeric `API_PORT` throws; unknown extra keys are ignored
- [v] test `no-process-env.test.ts` greps `apps/**/src` and `packages/**/src` (excluding `packages/config/src`) and fails on any `process.env` occurrence

## impl notes
- zod v4 (`import { z } from 'zod'`), version pinned through the T001 catalog so contracts/nestjs-zod/drizzle-zod all share one zod ← mixed zod majors break schema interop
- parsing at import time (module side effect) is intentional per ARCH-31: a bad env fails the process immediately instead of at first use
- for tests, expose `parseEnv(raw: Record<string,string|undefined>)` and have the module-level `env` call it with `process.env` — keeps the package unit-testable without mutating the real environment
- keep secrets out of the schema's error output (print keys, never values)

## result
- files: `packages/config/{package.json,tsconfig.json,tsconfig.build.json,src/env.ts,src/index.ts,src/env.test.ts}` `.env.example` `no-process-env.test.ts` `vitest.config.ts`(+`unit` project) `package.json`/`pnpm-lock.yaml`
- verify: 21 tests pass (tooling 13 + unit 8) · `pnpm turbo run lint typecheck test` 0 · `pnpm biome format --write .` no-op · spec lint clean
- both new invariants were proven to fail on violation: a planted `process.env` read in another package's `src/` made `no-process-env.test.ts` fail, and negating the secret-leak matcher made that assertion fail
- packaging convention set here for every internal package: `tsc -p tsconfig.build.json` emits **CommonJS + .d.ts** into `dist/`, exposed through `exports`. CJS is the only output that is safe before T003 picks a module format for `apps/api`, because ESM can import CJS but not the reverse — verified by `require()` and by an ESM named import of the built file
- consequence for the tasks that follow: `packages/tsconfig`'s `moduleResolution: bundler` is overridden to `node16` in each package's own `tsconfig.json` so typecheck and emit resolve identically, and `verbatimModuleSyntax` must be `false` there because ESM syntax cannot be emitted as CJS with it on
- root vitest gained a `unit` project matching `{apps,packages}/*/src/**/*.test.ts?(x)` and excluding `*.int.test.ts` — T005 adds the `int` project, T007 the web/e2e ones
- `no-process-env.test.ts` sits at the repo root so it runs in the `tooling` project next to the other repo-wide invariants, and it skips `.gen.ts` output
- `NODE_ENV` is required with no default, matching the acceptance list where only `LOG_LEVEL` and `API_PORT` name one; a missing env therefore fails the process at import (ARCH-31) and the message names all offending keys at once with no values
- no SSOT divergence
