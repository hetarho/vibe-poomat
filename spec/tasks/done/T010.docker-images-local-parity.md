# T010 docker images & local parity
> st:done@260907 | ssot:ARCH-29 ARCH-30 ARCH-3 ARCH-34 | base:ARCH@2 | dep:T005 T007

## goal
Multi-stage distroless Docker images for web and api plus a docker-compose stack (web, api, pg) that mirrors production locally.

## acceptance
- [v] `apps/api/Dockerfile` and `apps/web/Dockerfile`: multi-stage — deps (pnpm fetch/install with lockfile) → build (turbo build for that app) → runtime `gcr.io/distroless/nodejs22-debian12` running the built output as a non-root user
- [v] images build from the repo root context with a `.dockerignore` excluding `node_modules .turbo dist coverage .git`
- [v] `docker-compose.yml` extends the T005 file with `api` (depends_on pg healthy) and `web` (depends_on api) services, env from `.env`, ports published; the `minio` service added by T014 must keep working alongside
- [v] migrations are a distinct step, not app boot: a `migrate` one-shot compose service (or documented `pnpm db:migrate` invocation) runs before `api` accepts traffic (ARCH-13)
- [v] `docker compose up` yields: api `/health` 200 and `/ready` 200, web `/` served with SSR content
- [v] `scripts/docker-smoke.sh` builds both images, brings the stack up, polls `/health` `/ready` and web `/`, tears down, and exits non-zero on any failure; wired as `pnpm test:docker`
- [v] `pnpm test:docker` is NOT part of `pnpm turbo run test` (too slow for the inner loop) and is documented as the pre-deploy check
- [v] test: `docker-smoke.sh` is the automated verification for this task and must pass locally; its failure path is verified by pointing it at a stopped stack

## impl notes
- distroless has no shell: healthchecks cannot use `curl` inside the container — use compose-level healthchecks from the host or a tiny node one-liner as the CMD probe
- `pnpm deploy --filter=<app> --legacy` (or `--prod`) into `/app` in the build stage so the runtime image carries only that app's production deps ← keeps the monorepo out of the final layer
- web runs the TanStack Start node server output; do not serve it through a separate nginx — one process per image (ARCH-29)
- these images are built and smoke-tested locally only; pushing to GHCR and running them on the VPS behind Caddy is T016 (ARCH-30)

## result
- files: `apps/api/Dockerfile` · `apps/web/Dockerfile` · `.dockerignore` · `docker-compose.yml` (pg + migrate + api + web) · `apps/api/src/migrate.ts` · `scripts/docker-smoke.sh` · root `package.json` (`test:docker`)
- verify: `pnpm test:docker` exits 0 end to end — it builds both images, brings pg up, runs migrations to completion, waits for api and web to report healthy, then checks `/health` 200 `{"status":"ok"}`, `/ready` 200 with `"db":true`, and web `/` 200 containing the shell and the home heading, and tears the stack down. Its failure path was verified by pointing it at a stopped stack, where it exits 1
- also green: 157 tests and `pnpm turbo run lint typecheck test build` 17/17 with the new `src/migrate.ts` in the graph · `pnpm biome format --write .` no-op
- image sizes: api 305MB, web 207MB (uncompressed). `pnpm deploy --legacy --filter=api --prod /app` leaves the runtime image with only that app plus its production dependencies, and nitro bundles the web server so **that image carries no `node_modules` at all**
- migrations run as their own image entry point, `dist/migrate.js`, in the very same api image. That means a deploy applies exactly the migrations the image was built with, and it needs neither drizzle-kit nor a TypeScript loader at runtime — `drizzle-orm`'s programmatic `migrate()` is a production dependency already. The compose `api` service depends on `migrate` with `service_completed_successfully`, so it cannot accept traffic before the schema is current (ARCH-13)
- **distroless has no shell, no curl and no wget**, so both healthchecks are `/nodejs/bin/node -e "fetch(...)"`. The absolute path is required because a docker healthcheck does not go through the image's entrypoint
- `docker compose up -d --wait web` is what the smoke script uses: because of the depends_on chain, waiting on web alone waits on the whole stack, and the migrate step's exit status gates it
- `pnpm test:docker` is deliberately **not** a turbo task — `pnpm turbo run test` resolves to `build` and `test` only — so the inner loop stays fast and this stays the pre-deploy check
- the runtime user is `nonroot` in both images, and `.dockerignore` keeps `node_modules`, build output, `.git`, `.env`, coverage and report directories out of the build context
- the smoke teardown uses `--volumes`, so it leaves no database behind; `pnpm db:up` brings a fresh local one back
- images are built and smoke-tested locally only. Pushing to GHCR and running them behind Caddy on the VPS stays with T016 (ARCH-30)
- no SSOT divergence
