# T030 notification context: events, emails & preferences
> st:done@260908 | ssot:NOTI-1 NOTI-2 NOTI-3 NOTI-4 NOTI-5 NOTI-6 NOTI-7 AUTH-4 ARCH-35 ARCH-36 | base:NOTI@2 AUTH@2 ARCH@2 | dep:T013 T027

## goal
Every domain event that moves the loop becomes one immediate email, honouring per-type opt-out and carrying a deep link and unsubscribe link.

## acceptance
- [v] `apps/api/src/notification/` created with schema `notification_prefs(user_id uuid, type text, enabled boolean not null, updated_at, primary key(user_id, type))` — a missing row means enabled
- [v] event → email handlers for every NOTI-2 type: `feedback_received` (maker) · `thread_reply` (other participant) · `feedback_accepted` / `feedback_rejected` (feedbacker) · `auto_accept_warning` (maker) · `auto_accepted` (both) · `mission_ended` (maker, with the refund summary)
- [v] each handler resolves the recipient's provider email through the auth context's application service (AUTH-4) and enqueues `email.send`; nothing is sent inline (ARCH-36)
- [v] one email per event, no batching or digesting (NOTI-1, NOTI-6)
- [v] opt-out honoured per type; `auto_accept_warning` ignores the preference and always sends (NOTI-3)
- [v] `GET/PATCH /api/v1/notifications/preferences` (owner only) reads and updates the toggles; the warning type is returned as always-on and rejects a disable attempt with 422
- [v] every email body deep-links to the item and carries a per-type unsubscribe link; `GET /api/v1/notifications/unsubscribe?token=` disables that one type without a session — the token is an HMAC over `(userId, type)` with a config secret, constant-time compared (NOTI-4)
- [v] a deleted account's pending email jobs resolve to no recipient and exit cleanly instead of failing
- [v] React Email templates for all seven types in `packages/email`, each with subject, body copy, primary CTA and footer (sender per NOTI-5, "replies are not accepted")
- [v] no in-app inbox, push or digest (NOTI-7)
- [v] test: unit tests per handler — recipient resolution, opt-out respected, warning type sent even when disabled, deleted recipient short-circuits
- [v] test: unsubscribe token round trip; a tampered token is refused; the link disables exactly one type
- [v] test (int): a settle flow end to end enqueues exactly the expected email jobs (accept → feedbacker only; auto-accept → both), asserted against the console mailer
- [v] test: template snapshots for all seven (subject line + CTA URL + unsubscribe URL present)

## impl notes
- the notification context subscribes to other contexts' domain events (ARCH-39) and owns no business rule beyond delivery ← keeps NOTI out of the settle transaction
- preference rows are created lazily on first opt-out; a missing row meaning "enabled" avoids backfilling every user on every new event type
- unsubscribe is a GET without a session (people click it from a mail client), so the token must be unguessable and single-purpose — it disables one type and can never enable, delete, or reveal anything
- `NOTIFICATION_SECRET` added to `@repo/config`; rotating it invalidates old unsubscribe links, which is acceptable and documented in `.env.example`
- copy lives in the templates, not the api ← NOTI-5's brand voice changes must not touch domain code

### notes
- **Five handlers, seven types.** `slot_settled` is one event carrying three outcomes: the maker's yes, the maker's no, and the clock's yes — and only the last reaches both people. Splitting it into three subscriptions would have meant three places to get the recipient wrong.
- **The template names are the preference keys are the event types.** One list of seven strings, in the api's `NOTIFICATION_TYPES` and in `EmailTemplateProps`, so a toggle in settings and an email in an inbox cannot come to mean different things.
- **`REJECTION_REASONS` moved to the kernel** (in T029) and is now consumed by the rejection template's copy map, which turns each slug into a sentence.
- **The unsubscribe link answers with a 303 to the web settings page.** Whoever clicked is a person in a mail client, not a client library, and should land somewhere that shows them what changed. A tampered token is a 422 and a link for the always-on type is a 403 — a refusal is clearest as a status, and nobody reaches those by clicking a real link. `/settings/notifications?unsubscribed=<type>` is the route T039 must build.
- **The token has no expiry.** A link that stops working months later leaves somebody with no way out of an inbox; rotating `NOTIFICATION_SECRET` is the lever for invalidating them all, and the runbook says so.
- **The warning reads as on however its row is set.** A row could say otherwise — an older build, a hand-edited row — and the settings page must not promise silence it will not deliver.
- **A mission ending emails the owner, who is not on the event.** `MissionEnded` names the project but not its owner, so the owner comes through `MISSION_READER`, the port the project context already publishes. Adding an owner column to `missions` would have been the alternative and was not needed.
- **The deep links are declared, not discovered.** `DeepLinks` writes `/feedbacks/:id`, `/projects/:id` and `/settings/notifications`; T032-T038 must build those routes, and a mismatch is a diff in one file.
- **The handlers are five plain classes, not subclasses of a base.** A subclass with no constructor of its own emits no `design:paramtypes` and Nest cannot build it; three lines of repetition buy a graph that always resolves.
- **Every mission-settling test also queues `mission_ended`** — PROJ-6 completes the mission when its last slot settles, so an int test asserting "only the feedbacker was told" has to filter that one out. The helper that does so says why.

### ssot
Nothing diverges from NOTI-1..7, AUTH-4, ARCH-35 or ARCH-36; no `update-ssot` is needed. NOTI-4 asks every email to carry a per-type unsubscribe link and NOTI-3 forbids disabling the warning: the warning's footer therefore carries a settings link and a sentence saying why it cannot be switched off, which is the only reading that satisfies both.
