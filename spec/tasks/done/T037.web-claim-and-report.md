# T037 web: slot claim & report form
> st:done@260908 | ssot:FDBK-1 FDBK-2 FDBK-3 FDBK-4 FDBK-10 ARCH-6 ARCH-7 | base:FDBK@2 ARCH@2 | dep:T035 T025 T026

## goal
Pressing Start to hold a slot, then the fixed-shape report form that submits it.

## acceptance
- [v] Start button on a project with claimable slots: signed-out click opens sign-in with `returnTo`; owner never sees it; each rejection code renders its own message (`NO_SLOTS_AVAILABLE`, `ALREADY_CLAIMED`, `MISSION_NOT_OPEN`, `OWN_PROJECT`)
- [v] an active hold shows the remaining time until `held_until` (24h, FDBK-1) and a "give up the slot" action
- [v] the report form at `/missions/$id/report` renders exactly the FDBK-3 fields — first impression, where I got stuck, would I pay (yes/no + why), one suggestion, plus one input per mission question — each with a ≥20-character counter matching FDBK-10
- [v] the mission task text and questions are shown alongside the form so the feedbacker can follow them, together with the live URL link
- [v] a local draft is kept in `localStorage` per claim so a refresh does not lose the work; it is cleared on successful submit
- [v] submit is blocked client-side until every field passes, and server `details` still map onto fields when they disagree
- [v] after submit the form is replaced by a read-only view stating the report cannot be edited (FDBK-4) and that the maker has 72 hours
- [v] an expired hold renders as expired with a path back to claim again if slots remain
- [v] test: render tests — every FDBK-3 field present, a 19-character field blocks submit and names itself, all-valid enables it
- [v] test: the countdown renders from `held_until` and the expired state replaces the form
- [v] test: the draft survives a remount and is cleared after a successful submit
- [v] test: each claim rejection code renders its distinct message

## impl notes
- FSD: `features/claim-slot`, `features/submit-feedback` over `entities/mission` and `entities/feedback`, page at `pages/report`
- the draft is per-claim `localStorage` (client-only convenience, never authoritative) — a server-side draft would contradict FDBK-4's single-shot submission
- the countdown is derived from the server's `held_until`; the client clock is only used for the ticking display, and expiry is always confirmed by the server's rejection

## result
Files (web): `entities/feedback/{lib/report-rules.ts,lib/hold.ts,model/claim.query.ts}` (+tests), `entities/mission/model/mission.query.ts` (a mission by id), `features/claim-slot/*`, `features/submit-feedback/*`, `pages/report/*`, `app/routes/missions.$id.report.tsx`, the detail page's Start block, and a `localStorage` stand-in in `vitest.setup.ts`. Files (api): `GET /missions/:missionId/claims/me` (`ClaimSlotUseCase.mine`, `feedback.myClaimSchema`) and `GET /missions/:id` (`GetMissionsUseCase.byId`), both with int tests.

- Two more reads were missing, both needed before this page could exist at all: nothing could tell a client whether it already held a slot (the claim endpoints were POST and DELETE only), and nothing could read one mission by id — which `/missions/:id/report` knows and nothing else. `GET /missions/:missionId/claims/me` answers `{claim: Claim | null}`: wrapped rather than a bare nullable, so "you hold nothing" is a body somebody can read instead of an empty response to be guessed at. That is the fourth and fifth api gap in this batch of web tasks; the pattern is that read models for the web were never tasked (candidate for update-ssot or a create-task pass).
- `localStorage` is undefined under this vitest jsdom setup (node's own needs `--localstorage-file`, and the environment does not bridge jsdom's), so a small in-memory stand-in went into `vitest.setup.ts`. The feature code already treats storage as optional — every access is wrapped, and a blocked or private-mode browser simply gets no draft.
- The draft is read in an effect rather than during render: the server has no storage, and a value that differed between the two renders would be a hydration mismatch. It is cleared only on a successful submit, so a failed one loses nothing.
- Local field problems are shown only after a submit has been attempted, so an untouched form is not a wall of red; the server's `details` map still lands on the fields it names as soon as it disagrees.
- `StartControl` and `ClaimSlotBlock` are separate exports for the same reason `UpvoteControl`/`UpvoteButton` are (T035): FSD forbids `features/claim-slot` importing `features/auth`, so the sign-in wrapping is the page's decision and the presentational control is what the dialog triggers on.
- The countdown floors to whole minutes and re-reads the clock every 30s; the value always comes from the server's `held_until`, and a hold this browser thinks has lapsed still gets its real answer from the server's `CLAIM_EXPIRED`.
