# T033 web: profile & settings
> st:todo | ssot:AUTH-3 AUTH-6 AUTH-9 CRED-7 FDBK-8 ARCH-6 ARCH-37 | base:AUTH@2 CRED@2 FDBK@2 ARCH@2 | dep:T032 T020 T021

## goal
The public `/@handle` profile and the owner's settings page, including avatar upload, credit counters and account deletion.

## acceptance
- [ ] route `/@$handle` (SSR) renders display name, avatar, bio, external link, joined date, public credit counters (balance, received, given — CRED-7), maker rejection stats (FDBK-8, "no history yet" when null), the user's projects and the feedback they have given
- [ ] a 404 page for an unknown handle; the email is never rendered anywhere public (AUTH-4)
- [ ] `/settings` (owner only): edit display name, bio with a live 160-character counter, external link (https validation mirroring the server), avatar upload
- [ ] avatar upload flow: request the presigned URL, PUT the file directly to storage, submit the returned key, optimistic preview with rollback on failure; client-side type/size check mirrors the 2MB + png/jpeg/webp policy (T014)
- [ ] handle change field with availability feedback and the exact server error on collision; the copy states the old handle is released immediately and old links break (AUTH-6)
- [ ] notification preference toggles (T030) on the same settings page, with the auto-accept warning shown as always-on and disabled
- [ ] delete-account section: consequences listed verbatim from AUTH-9 (missions force-closed, pending feedback paid out, projects deleted, feedback kept as "deleted user", credits voided), a handle-typing confirmation, then sign-out and redirect home
- [ ] every server validation error renders on its field via the `details` map (T006)
- [ ] test: render tests — public profile hides owner-only affordances for a visitor and shows them for the owner; unknown handle renders 404; rejection stats render both the null and populated states
- [ ] test: settings form validation matches the server rules (bio 161 chars blocked, non-https link blocked, oversized/wrong-type avatar blocked before upload)
- [ ] test: the delete flow requires the exact handle and calls the endpoint once; a mismatch keeps the button disabled

## impl notes
- FSD: `pages/profile` and `pages/settings` compose `features/edit-profile`, `features/change-handle`, `features/delete-account`, `features/notification-preferences` over `entities/user` — each feature owns its mutation and cache invalidation
- the presigned upload happens in the browser, so the file never touches the api (ARCH-37); a failed PUT must not leave a stale key in the form state
- deletion consequences are copied from the SSOT decision so the UI cannot promise something the backend does not do
