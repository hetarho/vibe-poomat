# T008 web data layer
> st:todo | ssot:ARCH-7 ARCH-12 ARCH-16 ARCH-33 ARCH-6 | base:ARCH@2 | dep:T006 T007

## goal
Wire `@repo/api-client` into TanStack Query with SSR-safe hydration, typed error surfacing, and the Zustand store convention.

## acceptance
- [ ] a QueryClient is created per SSR request (never module-level) and dehydrated/hydrated through the root route, so no cache crosses requests
- [ ] default query options: `staleTime` 30s, `retry` disabled for `ApiError` with a 4xx status, one retry otherwise; mutations never retry
- [ ] `src/shared/api`: the api-client instance built from `API_URL` (server) / same-origin (browser) with `credentials:'include'`, plus re-exported `ApiError`
- [ ] `src/shared/api/error-message.ts`: maps `ApiError.code` → user-facing copy with a generic fallback; unknown codes never render raw server text
- [ ] `src/shared/store`: Zustand pattern (typed `create` wrapper, slice-per-file, selectors exported) used only for cross-slice client state (ARCH-7) — a README-less comment in `index.ts` states the rule
- [ ] TanStack Query is the only cache layer; no bespoke in-memory caches (ARCH-33)
- [ ] test: a 404 `{code}` response surfaces as `ApiError` and is not retried (retry spy count 0); a 500 retries once
- [ ] test: SSR hydration — a prefetched query renders its data on the server and the client mounts without an extra fetch
- [ ] test: two sequential SSR renders with different prefetched data do not leak state between QueryClients
- [ ] test: `error-message` returns the fallback copy for an unmapped code

## impl notes
- query keys: `[<entity>, <op>, params]` arrays defined next to each feature's api module (`features/<slice>/api`), never inline string keys ← makes invalidation greppable
- SSR fetches run server-side with the incoming `cookie` header forwarded to the api; the browser client relies on the cookie being same-site (ARCH-18 session cookie)
- error copy lives in the web layer, not the api: the api's stable `code` is the contract, the sentence is a UI decision (ARCH-17)
- no global loading/error boundary policy beyond route-level `errorComponent` + `pendingComponent`; features may add local handling
