# T020 profile read & update
> st:todo | ssot:AUTH-3 AUTH-4 AUTH-6 CRED-7 ARCH-16 ARCH-37 | base:AUTH@2 CRED@2 ARCH@2 | dep:T019 T014

## goal
Public profile by handle plus owner-only profile editing, including handle change and avatar upload.

## acceptance
- [ ] `GET /api/v1/users/by-handle/:handle` → public profile: handle, display name, avatar URL, bio, link, joined date; never the email (AUTH-4); 404 with `{code:"USER_NOT_FOUND"}` when unknown
- [ ] `PATCH /api/v1/users/me` updates display name, bio (≤160), link (https) and avatar key; partial updates only touch supplied fields
- [ ] `PATCH /api/v1/users/me/handle` changes the handle: validated by the `Handle` VO, rejected with `{code:"HANDLE_TAKEN"}` on collision; the old handle is released immediately and not redirected (AUTH-6)
- [ ] avatar flow: client asks T014 for an `avatar` presigned URL, uploads, then sends the returned key here; the api resolves it to a public URL on read and deletes the previous object in a job
- [ ] a profile with no uploaded avatar keeps the provider avatar URL from signup
- [ ] the public profile response reserves the credit fields (balance, received, given) required by CRED-7 — populated in T021, rendered as 0 until then, and the contract shape does not change afterwards
- [ ] test: use case unit tests — bio over 160 and non-https link rejected with `VALIDATION_FAILED` details naming the field; handle collision returns `HANDLE_TAKEN`; unchanged fields are untouched
- [ ] test (int): public endpoint never includes an email for any fixture; handle lookup is case-insensitive; changing a handle frees the old one for another account in the same test
- [ ] test (int): setting a new avatar key enqueues deletion of the previous object exactly once, and never for the provider-supplied URL

## impl notes
- handle change has no cooldown in v1 (AUTH-6 says editable, nothing about frequency); the throttler bucket on mutating routes is the only limiter
- the public profile is keyed by handle, not id, so the web route `/@handle` needs no id lookup; an id-based internal lookup stays available for other contexts
- avatar: store the object key in `users.avatar_url` only when uploaded, and keep provider URLs as absolute URLs — a discriminator (`avatar_key` vs `avatar_url`) would double the column count for one boolean; the resolver treats a value without a scheme as a storage key
