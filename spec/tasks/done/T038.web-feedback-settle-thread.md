# T038 web: feedback view, settle & thread
> st:done@260909 | ssot:FDBK-5 FDBK-6 FDBK-7 FDBK-8 FDBK-9 CRED-4 ARCH-6 | base:FDBK@2 CRED@2 ARCH@2 | dep:T037 T027 T028

## goal
Reading a feedback report publicly, the maker's accept/reject decision, and the two-party thread.

## acceptance
- [v] `/feedbacks/$id` renders the full report publicly (FDBK-9) with author handle/avatar or "deleted user", submission time, state, and — when rejected — the reason and note
- [v] the maker sees Accept and Reject on a pending report; Reject requires one of the three fixed reasons with an optional note (FDBK-6)
- [v] accept/reject show what happens to the credit before confirming (1 credit to the feedbacker / back to you — CRED-4)
- [v] a pending report shows the auto-accept deadline (submitted + 72h) to both parties, and the maker sees the 48h warning state (FDBK-7)
- [v] an auto-accepted report is labelled as such, distinct from a manual accept
- [v] the thread renders oldest-first with a reply box for the two participants only; everyone else sees it read-only (FDBK-5)
- [v] the maker's "feedback on my projects" inbox lists pending reports first with their deadlines
- [v] settling a report that has already been settled surfaces the `FEEDBACK_ALREADY_SETTLED` message and refreshes the view rather than retrying
- [v] test: render tests — settle controls appear only for the maker on a pending report; rejection requires a reason; the credit consequence copy matches the chosen action
- [v] test: deadline rendering from `submitted_at` for both the 48h and 72h markers; auto-accepted label distinct from accepted
- [v] test: the reply box is present for both participants and absent for a third party; a posted reply appears optimistically and rolls back on failure

## impl notes
- FSD: `features/settle-feedback`, `features/reply-thread` over `entities/feedback`, composed by `pages/feedback-detail` and `pages/maker-inbox`
- accepting invalidates the feedback, mission and credit balance queries together — a stale balance after a settle is the most visible cache bug in this app
- rejection copy repeats that the report stays public with its reason (FDBK-9), so makers are not surprised by their own rejection rate (FDBK-8)

## result
Files (web): `entities/feedback/{lib/settle-clock.ts,model/feedback.query.ts,ui/report-view.tsx}` (+tests), `features/settle-feedback/*`, `features/reply-thread/*`, `pages/feedback-detail/*`, `pages/maker-inbox/*`, `app/routes/{feedbacks.$id,inbox}.tsx`, an `/inbox` link in the header, and the plain anchors T033/T034 left behind turned into typed Links. Files (api): `GET /feedbacks/received` (repository `listReceivedBy`, `received-cursor.ts`, use case, int tests), `makerId` on the feedback response, and FDBK-7's two windows exported from `@repo/contracts` as hours.

- The sixth api gap: the maker's inbox had no endpoint. `feedbacks.maker_id` was already denormalised for FDBK-8 and AUTH-9, so `GET /feedbacks/received` answers from it with no cross-context join. Its cursor carries two keys — whether the row was still pending, then the id — because a one-key cursor cannot say where a two-key order stopped; it mirrors `feed-cursor.ts`.
- `makerId` was added to the feedback response so a reader can tell whether the settle controls and the reply box are theirs without reading the project. Going through the project would have failed exactly where FDBK-9 matters most: PROJ-8 answers 404 for a deleted project, and the report about it stays public.
- FDBK-7's 48h and 72h now live in `@repo/contracts` as hours, mirrored by the api's `submit-feedback.use-case.ts` which schedules the jobs from its own ms constants. Both sides render the same deadline from the same `submittedAt`.
- `useSettleFeedback` invalidates the credit read and the session counters along with the report, mission and lists — the impl note's warning about a stale balance after a settle. A `FEEDBACK_ALREADY_SETTLED` refusal re-reads the report rather than retrying, and says which of the two things happened (somebody settled it, or the clock did).
- A reply appears before the server acknowledges it, tagged with a `pending:` id so the optimistic row can be removed and replaced by the server's own; a failure takes it back out. The thread stays open on a settled report, because FDBK-5 sets no window and the exchange about a rejection is the one worth having.
- The inbox renders one list from the api's single pending-first ordering, split into "Waiting on you" and "Decided" headings — the ordering is the server's, the grouping is presentation.
- `vitest.setup.ts` gained a `localStorage` stand-in in T037; nothing here needed changing, but the profile page's test now mounts a router because its links became typed.
