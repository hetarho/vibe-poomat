# T036 web: mission management
> st:todo | ssot:PROJ-4 PROJ-5 PROJ-6 PROJ-13 CRED-3 CRED-5 ARCH-6 | base:PROJ@2 CRED@2 ARCH@2 | dep:T035 T023

## goal
The maker's mission surface: open a mission with escrow, watch its slots, close it early.

## acceptance
- [ ] "Open a mission" on the owner's project page: task text ≤1000 with counter, up to 3 questions ≤200 each (add/remove rows), slots 1-10 (PROJ-13)
- [ ] the form shows the escrow cost (= slots) against the current balance and blocks submission when the balance is short, with the same message the server's `INSUFFICIENT_CREDITS` produces (CRED-3)
- [ ] the control is unavailable with an explanation when a mission is already open on that project (PROJ-5)
- [ ] the mission panel shows state, slots claimable/held/submitted/settled, the expiry date (opened + 30 days), and the frozen task text and questions
- [ ] copy states that task text, questions and the live URL cannot change while the mission is open (PROJ-7)
- [ ] close action with a confirmation stating unfilled slots are refunded and held slots stay open until they resolve (PROJ-6, CRED-5)
- [ ] an expired mission renders as expired with its refund summary
- [ ] test: render tests — slot/character limits enforced, cost preview matches the slot count, insufficient balance disables submit with the reason
- [ ] test: the open control is hidden with an explanation when a mission is already open
- [ ] test: the close confirmation states the refund rule and calls the endpoint once

## impl notes
- FSD: `features/open-mission`, `features/close-mission` over `entities/mission`, composed into `pages/project-detail` for the owner view — visitors never load the owner bundle path
- the balance check is a UX affordance only; the authoritative rejection is the server's (T023), and the client must render that error even when its own check passed (stale balance)
- the expiry date is rendered from `opened_at + 30d` returned by the API, never computed from the browser clock
