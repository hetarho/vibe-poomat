# T011 transaction manager & domain event dispatch
> st:todo | ssot:ARCH-38 ARCH-39 ARCH-10 ARCH-11 ARCH-14 | base:ARCH@2 | dep:T004 T005

## goal
One database transaction per use case with repositories joining it implicitly, and domain events dispatched only after that transaction commits.

## acceptance
- [ ] `TransactionManager` port in `src/shared/application` with `run<T>(fn: () => Promise<T>): Promise<T>`; the Drizzle adapter opens a tx and stores it in `AsyncLocalStorage`
- [ ] `src/shared/db` exposes `getDb()` returning the ambient transaction when one is active, otherwise the pool client; every repository uses it and never receives a tx argument
- [ ] nested `run()` joins the outer transaction instead of opening a second one
- [ ] `AggregateRoot.pullEvents()` results are collected by a `DomainEventCollector` during the transaction and dispatched by an in-process `EventBus` only after commit; a rollback discards them
- [ ] handlers registered by decorator/token per event name; a handler failure is logged and does not roll back the (already committed) transaction
- [ ] handlers may call other contexts' application services or enqueue jobs (T012), never write inside the finished transaction — enforced by a runtime assertion that `getDb()` has no ambient tx inside a handler
- [ ] test (int): two repositories writing in one `run()` both roll back when the second throws
- [ ] test (int): nested `run()` shares one tx (assert with a `pg_current_xact_id`-style check or a rollback visibility assertion)
- [ ] test: events dispatched only after commit — a handler spy sees nothing when the tx throws, exactly once when it commits
- [ ] test: a handler that tries to reuse the committed tx trips the assertion

## impl notes
- AsyncLocalStorage over an explicit tx parameter ← ARCH-11 keeps `application`/`domain` framework-free; threading a Drizzle tx through every port signature would leak infrastructure into the use case signatures
- the collector lives in request scope, fed by repositories when they persist an aggregate (`repo.save()` drains `pullEvents()`); the aggregate never dispatches by itself
- at-most-once dispatch is acceptable here because anything that must not be lost (email, timers) is enqueued as a pg-boss job inside the transaction (T012), not done in a handler
- controllers do not open transactions; only use cases do — dependency-cruiser already forbids presentation → infrastructure
