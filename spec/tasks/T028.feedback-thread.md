# T028 feedback thread
> st:todo | ssot:FDBK-5 FDBK-9 AUTH-9 ARCH-17 | base:FDBK@2 AUTH@2 ARCH@2 | dep:T026

## goal
A public-readable reply thread on each feedback where only the maker and the feedbacker can post.

## acceptance
- [ ] schema `feedback_replies(id uuid pk, feedback_id uuid not null, author_id uuid, body text not null, created_at, index(feedback_id, created_at))`
- [ ] `POST /api/v1/feedbacks/:id/replies` — allowed only for the project owner and the report author (FDBK-5); anyone else gets 403 `{code:"NOT_A_THREAD_PARTICIPANT"}`
- [ ] body required, 1-2000 characters after trimming
- [ ] `GET /api/v1/feedbacks/:id/replies` is public with cursor pagination, oldest first; a reply from a deleted account shows a null author (AUTH-9)
- [ ] replies are allowed at any time after submit, including after the feedback is settled (FDBK-5 sets no window)
- [ ] each posted reply emits `ThreadReplied { feedbackId, authorId, recipientId }` for NOTI (T030) — the recipient is the other participant
- [ ] replies are immutable: no edit or delete endpoint in v1
- [ ] test: unit tests — a third party is refused, empty/oversized bodies rejected, the recipient in the event is always the other participant
- [ ] test (int): both participants can post, ordering and cursor paging are stable, a null author renders as deleted-user data
- [ ] test (int): posting on a settled feedback still works and still emits the event

## impl notes
- participants are resolved per request from the feedback row (`author_id`) and the project owner; there is no participants table ← the pair is fixed for the life of the thread
- `author_id` nullable for the same reason as the report (AUTH-9 anonymization)
- no read-receipts, reactions or nesting: FDBK-5 describes a flat two-party thread
