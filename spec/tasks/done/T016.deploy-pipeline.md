# T016 deploy pipeline
> st:done@260908 | ssot:ARCH-28 ARCH-29 ARCH-30 ARCH-13 | base:ARCH@2 | dep:T009 T010

## goal
Main-branch workflow that builds and pushes images to GHCR and rolls the VPS compose stack behind Caddy, running migrations first.

## acceptance
- [v] `.github/workflows/deploy.yml` on push to `main`: build both images with buildx + layer cache, tag `sha` and `latest`, push to GHCR
- [v] deploy job connects to the VPS over SSH (key from repository secrets), pulls the new tags, runs `db:migrate` as a one-shot container, then `docker compose up -d` for api and web
- [v] deploy aborts before switching traffic if the migration container exits non-zero
- [v] `Caddyfile` committed: TLS automation, reverse proxy `/api/*` → api and everything else → web, gzip, sane security headers; Caddy runs in the same compose stack
- [v] a post-deploy smoke step polls `/health` and `/ready` and the web root through the public domain; a failure fails the workflow (and logs the previous image tag for a manual roll back)
- [v] `.env.production` is NOT in the repo; the workflow renders the server env from GitHub secrets
- [v] documented roll back: re-run the deploy job pinned to the previous image sha
- [v] test: `actionlint` passes on the new workflow; a dry-run job (`workflow_dispatch` with `deploy: false`) proves build+push steps without touching the server
- [v] test: the smoke script from T010 is reused against the deployed domain so there is exactly one implementation of "is it up"

## impl notes
- SSH + compose rather than a registry-webhook agent ← ARCH-30 is a single VPS; the simplest thing that can also roll back by tag
- migrations run as their own container from the freshly built api image, before `up -d`, per ARCH-13 (never on app boot)
- image tags: immutable `sha-<short>` is what deploys; `latest` exists only for humans
- concurrency: `group: deploy`, `cancel-in-progress: false` — cancelling mid-deploy could leave the stack half-rolled
