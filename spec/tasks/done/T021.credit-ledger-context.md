# T021 credit ledger context
> st:done@260908 | ssot:CRED-1 CRED-2 CRED-3 CRED-4 CRED-5 CRED-6 CRED-7 CRED-9 AUTH-2 ARCH-13 ARCH-14 ARCH-38 ARCH-39 | base:CRED@2 AUTH@2 ARCH@2 | dep:T018 T012

## goal
The append-only credit ledger with derived balances, the seed grant on account creation, and the escrow/payout/refund/void operations other contexts call.

## acceptance
- [v] `apps/api/src/credit/` context created (ARCH-34) with schema:
      `ledger_entries(id uuid pk, account_id uuid not null, type text not null, balance_delta integer not null, escrow_delta integer not null, ref_type text not null, ref_id uuid, created_at, index(account_id, created_at), unique(type, account_id, ref_type, ref_id) where ref_id is not null)`
      `credit_accounts(account_id uuid pk, balance integer not null default 0, escrowed integer not null default 0, received integer not null default 0, given integer not null default 0, updated_at, check(balance >= 0), check(escrowed >= 0))`
- [v] every movement writes one ledger entry AND updates the cached `credit_accounts` row in the same transaction; nothing else ever writes those columns (CRED-6)
- [v] types: `seed` `escrow` `payout` `refund` `void` with fixed delta signs — seed(+balance), escrow(−balance,+escrow), payout(−escrow on maker, +balance on feedbacker as two entries), refund(−escrow,+balance), void(−balance and/or −escrow)
- [v] application services other contexts call: `grantSeed(userId)` · `escrowForMission(userId, missionId, n)` · `settleSlot(missionId, feedbackId, to: 'feedbacker'|'maker', makerId, feedbackerId)` · `refundUnfilled(missionId, makerId, n)` · `voidAccount(userId)` — each idempotent on its `(type, account, ref)` key
- [v] `escrowForMission` returns `InsufficientCreditsError` when balance < n; the DB check constraint is the backstop, not the primary check (CRED-3)
- [v] `AccountCreated` handler grants 2 seed credits exactly once per account (CRED-2, AUTH-2); a replayed event is a no-op thanks to the unique key
- [v] `GET /api/v1/credits/me` returns balance, escrowed and the ledger page (cursor, newest first) — owner only; the public counters (balance, received, given) are exposed through the profile response (CRED-7)
- [v] balances are never edited directly and there is no admin adjustment path (CRED-10)
- [v] test: unit tests per operation asserting the exact entry pair and deltas, and that every operation is a no-op on replay
- [v] test: insufficient balance blocks escrow and writes nothing
- [v] test (int): invariant property test — after a randomized sequence of seed/escrow/settle/refund/void across several accounts, for every account `balance + escrowed == Σ(seed+payout+refund) − Σ(escrow+void)` and the cached row equals the recomputed sums
- [v] test (int): concurrent escrow attempts on the same account with balance for only one — exactly one succeeds (row lock), the other gets `InsufficientCreditsError`

## impl notes
- cached balances in `credit_accounts` beside the append-only log ← CRED-6 demands derived balances, but a `SUM()` per feed render is not viable; the invariant test is what keeps the cache honest, and the check constraints make an impossible state unwritable
- concurrency: `SELECT ... FOR UPDATE` on the `credit_accounts` row before any movement — the whole flow is already inside one transaction (ARCH-38)
- `received`/`given` counters increment on payout only (they are the public reciprocity signal, CRED-7); they are not derivable from balance alone once credits are spent
- credits are whole integers, never negative, no transfers between accounts (CRED-1) — there is deliberately no generic `transfer(from,to)` API, only the named operations above
- the account id IS the user id; the credit context stores it as a plain uuid with no FK to auth (ARCH-14)
