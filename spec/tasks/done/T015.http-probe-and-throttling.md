# T015 outbound HTTP probe & rate limiting
> st:done@260907 | ssot:ARCH-40 ARCH-41 ARCH-12 ARCH-17 | base:ARCH@2 | dep:T003

## goal
A SSRF-guarded outbound HTTP port for verifying user-supplied URLs, plus throttling on auth and mutating endpoints.

## acceptance
- [v] `HttpProbe` port: `probe(url): Promise<Result<{ finalUrl, status }, DomainError>>`; adapter uses `undici` with a custom connector that re-checks the resolved IP for every connection
- [v] rejects: non-https schemes, hosts resolving to private/loopback/link-local/CGNAT/metadata ranges (IPv4 and IPv6, including IPv4-mapped), credentials-in-URL, non-standard ports
- [v] follows at most 3 redirects, re-validating the destination on each hop; total timeout 5s; response body read capped at 64KB and discarded
- [v] HEAD first, falling back to a ranged GET when HEAD is not allowed (405/501); a 2xx or 3xx-terminating-in-2xx counts as reachable, everything else returns a typed `UrlUnreachableError` with the observed status
- [v] `@nestjs/throttler` configured with PG-backed storage: strict bucket on `/auth/*` and every mutating route (keyed by session user id when present, else client IP behind the proxy via a trusted `X-Forwarded-For` hop count), loose global bucket on reads
- [v] a throttled request returns 429 with the standard `{code:"RATE_LIMITED", message}` body from the T004 filter, not the throttler default
- [v] test: table-driven SSRF cases (127.0.0.1, 10.x, 169.254.169.254, `[::1]`, `::ffff:127.0.0.1`, a public host that redirects to 127.0.0.1) all rejected; a public https host accepted — DNS resolution stubbed, no live network in tests
- [v] test: timeout and 64KB cap enforced against a local test server that stalls / streams forever
- [v] test (int): exceeding the mutating-route bucket returns 429 with the standard error shape; the counter is keyed by user when authenticated

## impl notes
- the redirect re-check is the part that matters: validating only the first hop is the classic SSRF bypass, so the connector — not a pre-flight lookup — enforces the rule at connect time
- undici over global fetch ← it exposes the connector/dispatcher hook needed for per-connection IP checks
- probe results are not cached in v1: PROJ-2 checks once at project creation, so a cache would only add staleness
- the throttler needs `trustProxy` configured on Fastify consistently with the Caddy deployment (ARCH-30): exactly one proxy hop

- **taken before T014**, whose upload endpoint needs this throttler; both were unblocked, so the order was swapped rather than building the endpoint unguarded
- the SSRF guard lives in the undici **connector**, which is the only place that sees every hop: undici connects once per redirect, so a pre-flight lookup would validate the first URL and nothing else. The connector resolves the host itself, refuses if **any** answer is non-public, and then connects to the address it just checked while keeping the original hostname for TLS — so a second resolution cannot slip a different IP in
- the SSRF cases are table-driven with a stubbed resolver and no live network: loopback anywhere in 127/8, 0.0.0.0, all three private ranges, CGNAT, link-local including 169.254.169.254, multicast, reserved, `::1`, `::`, `fd00::`, `fe80::`, `ff02::`, and both IPv4-mapped forms; a host answering with one public and one private address is refused outright
- the probe walks redirects itself (undici 8 dropped `maxRedirections` from `request`), re-running the shape and address checks on every hop, HEADs first and falls back to a **ranged GET** on 405/501. Its timeout and 64KB cap are driven against a local server that stalls and one that streams forever: the streaming case finishes well inside the timeout, which is what proves the cap rather than the abort ended it
- the throttler storage is one PostgreSQL statement per request — open a window, expire a stale one, count the hit, start a block past the limit — so two concurrent requests cannot both "be first". Its behaviour is asserted against a real database: counting inside a window, blocking with a remaining time, a fresh window after expiry, and buckets with the same key under different throttler names staying apart
- **`trustProxy: 1` was missing and the tests found it.** Without it Fastify never derives a client IP from `X-Forwarded-For`, so every caller shared one bucket; the "counts each caller separately" test failed until the adapter was configured for exactly one Caddy hop (ARCH-30). `trackerFor` now reads `request.ip` alone, so the hop count is decided in one place
- 429 renders through T004's filter as `{code:'RATE_LIMITED', message}` and nothing else — the code map's 429 entry changed from `TOO_MANY_REQUESTS`, and the web's error copy followed
- **found and fixed a silent no-op in the parity stack**: `migrate` declared its own build, so it became a third image, and `docker-smoke.sh` builds only `api` and `web`. The migration container therefore ran a stale image and logged "migrations applied" while applying nothing — reproduced deterministically on a fresh volume. It now shares the api's image tag, so building the api updates it and a deploy can never migrate from an older build than it runs
- a useful consequence: because the throttler guard writes to `rate_limits` on **every** request, `/ready` answering 200 in the smoke now transitively proves the migration ran. That is what turned this bug from invisible into a failing smoke
- the first real migration is committed here (`rate_limits`), which also exercised the T005 generate/migrate pipeline end to end for the first time
- one deterministic test change: the expired-window case pushes `expires_at` into the past instead of sleeping. A sleep long enough to be reliable under a parallel `turbo run` was flaky at 1.2s and would only have made the suite slower
- no SSOT divergence
