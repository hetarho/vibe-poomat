# T036 web: mission management
> st:done@260908 | ssot:PROJ-4 PROJ-5 PROJ-6 PROJ-13 CRED-3 CRED-5 ARCH-6 | base:PROJ@2 CRED@2 ARCH@2 | dep:T035 T023

## goal
The maker's mission surface: open a mission with escrow, watch its slots, close it early.

## acceptance
- [v] "Open a mission" on the owner's project page: task text ≤1000 with counter, up to 3 questions ≤200 each (add/remove rows), slots 1-10 (PROJ-13)
- [v] the form shows the escrow cost (= slots) against the current balance and blocks submission when the balance is short, with the same message the server's `INSUFFICIENT_CREDITS` produces (CRED-3)
- [v] the control is unavailable with an explanation when a mission is already open on that project (PROJ-5)
- [v] the mission panel shows state, slots claimable/held/submitted/settled, the expiry date (opened + 30 days), and the frozen task text and questions
- [v] copy states that task text, questions and the live URL cannot change while the mission is open (PROJ-7)
- [v] close action with a confirmation stating unfilled slots are refunded and held slots stay open until they resolve (PROJ-6, CRED-5)
- [v] an expired mission renders as expired with its refund summary
- [v] test: render tests — slot/character limits enforced, cost preview matches the slot count, insufficient balance disables submit with the reason
- [v] test: the open control is hidden with an explanation when a mission is already open
- [v] test: the close confirmation states the refund rule and calls the endpoint once

## impl notes
- FSD: `features/open-mission`, `features/close-mission` over `entities/mission`, composed into `pages/project-detail` for the owner view — visitors never load the owner bundle path
- the balance check is a UX affordance only; the authoritative rejection is the server's (T023), and the client must render that error even when its own check passed (stale balance)
- the expiry date is rendered from `opened_at + 30d` returned by the API, never computed from the browser clock

## result
Files (web): `entities/mission/*` (PROJ-13 rules, missions query, `MissionPanel`), `entities/credit/*` (CRED-7 owner read), `features/open-mission/*`, `features/close-mission/*`, `pages/project-detail/ui/owner-mission-block.tsx` + the detail page and its route. Files (api): `GET /projects/:projectId/missions` (repository `listForProject`, `GetMissionsUseCase`, int tests) and `occupancy` on the mission response.

- A third api gap, of the same kind as T035's: there was no way to read a mission at all. Only the mission that is still open reached the client, as `project.activeMission`, so a closed or expired mission — and therefore PROJ-6's state and CRED-5's refund summary — was unreachable, as were the frozen task text and questions PROJ-7 talks about. Added `GET /projects/:projectId/missions` (public, newest first) and put the slot breakdown on the response: `occupancy` is `{claimable, held, submitted, settled}`, which the acceptance asks the panel to show and which `openSlots` alone could not express. `toMissionView` now takes the occupancy and derives `openSlots` from it, so the two can never disagree.
- The panel replaced T035's thin activeMission summary on the detail page, and that task's two assertions about it were updated to read the panel instead. The detail route now loads the mission list for everybody, because the task and the questions are what a feedbacker works from (T037 needs the same read).
- The owner's controls are a `lazy()` default export (`owner-mission-block.tsx`), so a visitor's browser never fetches them — the build emits `owner-mission-block-*.js` at ~7kB as its own chunk. The credit read lives inside it for the same reason: a visitor must not cause a request for somebody else's balance (CRED-7).
- The acceptance names the server's refusal `INSUFFICIENT_CREDITS`; the code the api actually answers with is `CREDIT_INSUFFICIENT` (`credit/domain/credit-errors.ts`). Implemented against the real one. The form renders it even when its own balance check passed, which is the stale-balance case the impl notes call out.
- The refund summary is derived from the current occupancy rather than a stored number: `refundedSlots` exists only on the `MissionEnded` event, not on the mission row. That is honest for what CRED-5 does today, but it means a slot released after the mission ended changes the number the page shows. Whether releasing a held slot on an ended mission refunds its credit is worth checking — candidate for review-code.
