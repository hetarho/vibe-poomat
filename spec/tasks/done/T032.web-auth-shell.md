# T032 web: auth shell & sign-in
> st:done@260908 | ssot:AUTH-1 AUTH-8 ARCH-5 ARCH-6 ARCH-7 ARCH-18 | base:AUTH@2 ARCH@2 | dep:T008 T019

## goal
Sign-in entry points, SSR-resolved session state, and the header auth slot the rest of the UI builds on.

## acceptance
- [v] `entities/session` slice: an SSR loader reading `/auth/me` with the incoming cookie forwarded, exposing `useCurrentUser()` (null when signed out) — no client-side flash of the wrong state
- [v] `features/auth` slice: `SignInDialog` with GitHub and Google buttons linking to `/api/v1/auth/:provider` with `returnTo` set to the current path; no email/password field anywhere (AUTH-1, AUTH-10)
- [v] header auth slot (the placeholder from T007) renders avatar + menu (profile, settings, sign out) when signed in, otherwise the sign-in trigger
- [v] sign-out posts to `/auth/logout` and clears the cached session query
- [v] `?error=` on the landing route surfaces a human message per error code from the callback (T018), including the "provider has no verified email" case
- [v] a route-level guard helper redirects signed-out users away from owner-only pages to sign-in with `returnTo`
- [v] session state lives in TanStack Query, not Zustand ← it is server state (ARCH-7)
- [v] test: render tests — signed-out header shows the sign-in trigger, signed-in shows the menu; each provider button targets the right URL with an encoded `returnTo`
- [v] test: the error banner maps every callback error code and falls back for an unknown one
- [v] test: the guard helper redirects when signed out and renders children when signed in

## impl notes
- the session query is prefetched during SSR so the first paint already knows who you are; the QueryClient-per-request rule from T008 is what makes that safe
- FSD placement: `entities/session` owns the query and types, `features/auth` owns the interactions, `widgets/header` composes them — no upward imports (ARCH-6)
- the sign-in trigger is a dialog rather than a route so `returnTo` is always the page you were on

### notes
- **The guard is a `beforeLoad` helper, not a component.** The acceptance says "renders children when signed in", but a component that redirects during render is exactly the flash the first acceptance item forbids: `beforeLoad` runs on the server, so a signed-out person gets a real redirect and never sees the page at all. The test proves the equivalent pair — it throws a redirect carrying `returnTo` when signed out, and returns the account when signed in.
- **Signed out is `null`, not an error.** `fetchCurrentUser` resolves a 401 to null and lets everything else through, so no consumer has to tell "not signed in" apart from "the api is down". A test pins both directions.
- **The dialog reads `returnTo` from the router**, which is the whole reason it is a dialog: the path is the page somebody was actually on. `/sign-in` exists only for the two cases with no such page — a failed callback and the guard.
- **`/sign-in` is the api's `SIGN_IN_PATH`**, which the callback already redirects to with `?error=`. Every code T018 can send has a sentence of its own; an unknown one falls back rather than echoing the code at the reader, and a test walks the whole list.
- **The account menu links with plain anchors for now.** `/users/$handle` and `/settings` are T033's routes, and the typed `Link` will not compile against routes that do not exist. T033 converts them.
- **Sign-out sets the session to null rather than invalidating it**, so the header changes in the same tick instead of showing the old avatar until a refetch lands; everything else in the cache was read as that person, so it is all invalidated.
- **The smoke test now asserts the server-rendered header.** `Sign in` appearing in the HTML from the container proves the SSR round trip — the cookie forward, the api call, the prefetch and the hydration — which no render test can.
