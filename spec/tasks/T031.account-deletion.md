# T031 account deletion
> st:todo | ssot:AUTH-9 AUTH-12 CRED-8 PROJ-6 PROJ-8 FDBK-9 CRED-4 ARCH-38 | base:AUTH@2 CRED@2 PROJ@2 FDBK@2 ARCH@2 | dep:T027 T023 T021

## goal
Self-serve immediate deletion that force-closes missions, pays out pending feedback, voids credits and anonymizes what others received.

## acceptance
- [ ] `DELETE /api/v1/users/me` runs the ordered sequence in one transaction (AUTH-9): force-close the user's active missions (refunding unfilled slots, PROJ-6) → auto-accept every pending feedback on those missions so feedbackers are paid (CRED-4) → delete the user's projects and missions → set `author_id = null` on feedback and replies the user wrote (FDBK-9) → void remaining balance and escrow (CRED-8) → delete sessions, identities and the user row
- [ ] the user's own held claims are released so their slots return to other missions
- [ ] deletion is irreversible with no grace period; the endpoint requires a typed confirmation field matching the account handle
- [ ] after deletion the session cookie is cleared and every prior session is gone
- [ ] public reads keep working: feedback the user gave stays visible with a null author, projects they owned are gone from the feed
- [ ] the credit invariant holds after voiding (the void entries balance the ledger, CRED-6)
- [ ] no admin path exists — only the account owner can trigger this (AUTH-12)
- [ ] test (int): full-scenario fixture — a user with an open mission (2 unfilled slots, 1 pending feedback), a given feedback, a balance and an escrow; after deletion assert every one of the AUTH-9 outcomes including the paid feedbacker and the voided remainder
- [ ] test (int): the ledger invariant recomputes correctly for every surviving account afterwards
- [ ] test (int): a wrong confirmation string aborts and changes nothing; the whole sequence rolls back if any step fails
- [ ] test: unit test asserting the step order (a paid-then-voided ordering is what makes feedbackers whole)

## impl notes
- one transaction across four contexts is exactly what ARCH-38 was decided for; each context exposes a `purgeUser(userId)`-style application service and this use case orchestrates the order
- ordering matters and is asserted: auto-accepting BEFORE voiding is the difference between paying feedbackers and stealing their credits (AUTH-9)
- anonymization is a null `author_id`, never a deletion of the feedback (FDBK-9) — the value others received survives
- deletion runs inline rather than as a job so the user sees the result immediately; the object-storage cleanup for their images is the one part deferred to a job (best-effort, T014)
