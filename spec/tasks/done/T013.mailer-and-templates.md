# T013 mailer port, Resend adapter & email templates
> st:done@260907 | ssot:ARCH-36 ARCH-35 ARCH-31 ARCH-34 | base:ARCH@2 | dep:T012

## goal
A `Mailer` port whose Resend adapter sends React Email templates from a background job, with a console adapter for development and test.

## acceptance
- [v] `Mailer` port in `src/shared/application`: `send({ to, template, props })` — the port takes a template name + typed props, never raw HTML
- [v] `packages/email`: React Email components + a `render(template, props)` returning `{ subject, html, text }`; templates typed by a discriminated union so an unknown name fails typecheck
- [v] Resend adapter in production; console adapter (logs subject + recipient + a rendered text preview) in development/test — selected by `NODE_ENV`/`MAIL_DRIVER` in `@repo/config`, never by a branch inside a use case
- [v] sending always goes through the `email.send` job (T012): callers enqueue, the handler renders and calls the port
- [v] from address and display name come from config (`MAIL_FROM`, `MAIL_FROM_NAME`); every template renders the "replies are not accepted" line and a footer slot for the unsubscribe link that T030 fills
- [v] a Resend API failure throws so pg-boss retries; a 4xx from Resend (bad address) is treated as permanent and dead-letters immediately without retry
- [v] one placeholder template (`account-welcome`) proves the pipeline end to end; the real templates arrive with T030
- [v] test: `render` snapshot for the placeholder template (subject, text fallback present, HTML contains the CTA URL)
- [v] test: the console adapter records the send in dev; the Resend adapter is called with the rendered payload (HTTP stubbed)
- [v] test (int): enqueueing `email.send` runs the handler once and calls the mailer once; a retriable failure is retried, a 4xx is not

## impl notes
- templates live in `packages/email` rather than the api so that copy changes never rebuild api domain code, and so the web app could preview them later ← the api adapter only imports `render`
- text fallback is mandatory (deliverability): React Email's plain-text renderer, not a hand-written duplicate
- config keys added here: `MAIL_DRIVER` (resend|console), `RESEND_API_KEY` (required only when driver=resend, conditional zod refinement), `MAIL_FROM`, `MAIL_FROM_NAME`
- no queue-level dedupe of identical emails: NOTI-1 is one email per event, and job idempotence already prevents double sends of the same job

## result
- files: `packages/email/**` (layout, `account-welcome`, `render`, 5 tests) · `apps/api/src/shared/application/{mailer,job-scheduler,index}.ts` · `apps/api/src/shared/infrastructure/mail/{console-mailer,resend-mailer,send-email.job,mail.module,index}.ts` + `mailer.test.ts` `mail.int.test.ts` · `apps/api/src/shared/infrastructure/jobs/pg-boss.service.ts` · `apps/api/src/app.module.ts` · `packages/config/src/env.ts` + tests · `.env.example` · both `Dockerfile`s
- verify: 216 tests pass (root 54 + web 30 + api unit 111 + api int 21) · `pnpm turbo run lint typecheck test build` 19/19 · `depcruise src` clean over 91 modules · coverage gate exits 0 · `pnpm test:docker` exits 0 with the mail module in the boot path
- the integration tests drive the real path against a real database: one enqueued job sends exactly once, a transient failure is retried and then succeeds, a `PermanentJobFailure` lands in `email.send.dead-letter` **without** the mailer ever being called again, and an email enqueued in a rolled-back use case leaves no job at all
- **`PermanentJobFailure` is a new, general capability**, added to the job port rather than to the mailer: a handler that throws it has its job sent straight to the dead-letter queue instead of retried. Without it there is no way to say "this will never succeed" to pg-boss, which retries every throw
- the Resend adapter talks to the **REST API with `fetch`** instead of the SDK, because the retry decision needs the HTTP status: a 4xx (a rejected address) is permanent, a 5xx is not. That also drops a dependency and makes the adapter trivially stubbable — the tests inject a fetch and assert the exact posted payload
- `MAIL_DRIVER`/`RESEND_API_KEY` are validated **as a pair** with a zod `check`, so choosing the Resend driver without a key fails at boot rather than at the first send
- the text fallback comes from `@react-email/render`'s `toPlainText` over the rendered HTML, never a hand-written duplicate. It upper-cases headings, which the render test states explicitly rather than working around
- the template map is a keyed type (`EmailTemplateProps`), so `render(name, props)` reads as the acceptance describes while an unknown name still fails typecheck; `templateNames()` is asserted so a template added without registering it shows up
- the layout renders the no-reply notice exactly once and carries an optional `footer` slot, which is where T030's unsubscribe link goes
- **fixed a real Dockerfile bug the new package exposed**: the deps stage listed workspace manifests one by one, so `packages/email` was missing and its build failed inside the image. Both Dockerfiles now use `COPY --parents apps/*/package.json packages/*/package.json ./` (needing `dockerfile:1.7-labs`), which keeps the dependency layer cacheable and needs no edit when a package is added
- the job wait windows in both int suites were widened to 45s after a single unreproducible failure during a parallel `turbo run`; two full runs under six busy CPU loops then passed, the same way T005's flake was settled
- no SSOT divergence
