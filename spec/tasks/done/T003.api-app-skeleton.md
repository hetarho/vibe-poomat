# T003 api app skeleton
> st:done@260907 | ssot:ARCH-9 ARCH-17 ARCH-31 ARCH-32 ARCH-34 ARCH-3 | base:ARCH@2 | dep:T002

## goal
Runnable `apps/api` NestJS 11 + Fastify app with pino request-scoped logging, `/health` `/ready`, and config wired through `@repo/config`.

## acceptance
- [v] `pnpm --filter api dev` boots on `API_PORT` with the Fastify adapter; `pnpm --filter api build` emits a runnable `dist/main.js`
- [v] global prefix `/api/v1` (ARCH-17); `/health` and `/ready` are excluded from the prefix and live at the root
- [v] `/health` → 200 `{"status":"ok"}` unconditionally (liveness)
- [v] `/ready` → 200 `{"status":"ready","checks":{...}}` when every registered readiness indicator passes, 503 `{"status":"not-ready","checks":{...}}` otherwise; the indicator registry is empty here and T005 registers the DB check
- [v] pino JSON logs via nestjs-pino: every log line carries `reqId` taken from the `x-request-id` header when present, otherwise a generated UUIDv7; `LOG_LEVEL` from config; `authorization`/`cookie` headers redacted
- [v] `app.enableShutdownHooks()` with graceful Fastify close
- [v] structure follows ARCH-34: `src/main.ts`, `src/app.module.ts`, `src/shared/` — no bounded context yet
- [v] test: contract tests (Nest testing module + `app.inject`) for `/health` 200 and `/ready` 200-with-no-indicators and 503-with-a-failing-fake-indicator
- [v] test: unit test asserting an inbound `x-request-id` appears as `reqId` in the emitted log record (pino destination stubbed)

## impl notes
- `@nestjs/platform-fastify` (ARCH-9); do not add `@nestjs/platform-express` — two adapters in the tree invite the wrong import
- config: a thin `ConfigModule` provider that re-exports `@repo/config`'s `env` under a `Symbol('ENV')` token, so application code injects it instead of importing a module singleton (ARCH-11 keeps framework-free layers testable)
- readiness registry: `ReadinessRegistry` service in `src/shared/health` holding `{ name, check(): Promise<boolean> }` entries; modules register their own indicator in `onModuleInit` ← lets T005 add PG without editing the health controller
- CORS: allow `WEB_URL` only, `credentials: true` — needed for the cookie session in the AUTH tasks
- no global validation pipe here; it arrives with nestjs-zod in T006

## result
- files: `apps/api/{package.json,nest-cli.json,tsconfig.json,tsconfig.build.json,vitest.config.ts,vitest.setup.ts}` · `apps/api/src/{main.ts,app.module.ts,bootstrap.ts,bootstrap.test.ts}` · `apps/api/src/shared/config/{env.token.ts,config.module.ts}` · `apps/api/src/shared/health/{readiness-registry.ts,health.controller.ts,health.module.ts,+2 tests}` · `apps/api/src/shared/logging/{logger.module.ts,request-id.ts,logger.module.test.ts}` · `apps/api/src/test-support/fake-env.ts` · `biome.json` `tooling.test.ts` `vitest.config.ts` `pnpm-workspace.yaml`
- verify: 39 tests pass (root 23 + api 16) · `pnpm turbo run lint typecheck test build` 8/8 · `pnpm biome format --write .` no-op · spec lint clean · `dist/main.js` and `pnpm --filter api dev` both boot and answer `/health` 200, `/ready` 200, `/api/v1/health` 404, SIGTERM shuts down cleanly
- request id is owned by Fastify, not pino: `requestIdFastifyOptions` sets `requestIdHeader: 'x-request-id'` plus a UUIDv7 `genReqId`, and `quietReqLogger` binds `reqId` onto the per-request child logger so every line of a request carries it exactly once ← pino-http's own `genReqId` never fires under Fastify, which already assigns `req.id`
- **Biome's `style/useImportType` is off for `apps/api/**` and that is load-bearing.** Its autofix rewrote `import { ReadinessRegistry }` into `import type`, swc then emitted `Object` for that constructor parameter, and NestJS DI failed with "can't resolve dependencies". `tooling.test.ts` now asserts the override, and the contract tests fail loudly if a value import is converted again
- `javascript.parser.unsafeParameterDecoratorsEnabled` had to be turned on in `biome.json` or Biome cannot parse any NestJS parameter decorator (`@Res`, `@Body`, `@Inject`); also asserted in `tooling.test.ts`
- vitest transpiles api sources with `unplugin-swc` because esbuild cannot emit decorator metadata. Two traps found: vitest silently ignores a `vitest.config.mts` (it must be `.ts`), and plugins declared in a config referenced from the root `projects` list are not applied. Apps therefore own their own `test` script and turbo orchestrates them; the root config keeps only the `tooling` and `unit` (packages) projects
- `apps/api/tsconfig.json` covers `src` only — the vitest config and setup file stay out of typecheck because tsc treats this CommonJS package's ESM tooling files as errors; the suite itself is the check on them
- `uuid` is pinned to **10.0.0** plus `@types/uuid@10.0.0`: uuid 11+ is ESM-only, and `require()`-ing ESM needs Node 22.12+, which `engines: node >=22` does not guarantee. uuid 10 ships a CJS build and already exposes the `v7`/`validate`/`version` helpers T004's `EntityId` needs
- `fastify@5.11.3` is a direct dependency (matching what `@nestjs/platform-fastify@11.2.3` resolves) because pnpm's strict store does not expose transitive types
- `@swc/core` was added to `pnpm-workspace.yaml`'s `onlyBuiltDependencies`
- `/ready` answers through `@Res({ passthrough: true })` rather than throwing, so the probe never travels through the domain error mapper T004 installs
- CORS advertises the single configured `WEB_URL` to every caller, which is how a string origin behaves — the browser is the party that rejects a mismatch; the contract test states it that way
- no SSOT divergence
