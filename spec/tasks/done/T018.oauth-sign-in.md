# T018 OAuth sign-in & session issue
> st:done@260908 | ssot:AUTH-1 AUTH-2 AUTH-3 AUTH-4 AUTH-5 AUTH-6 AUTH-10 AUTH-11 ARCH-18 ARCH-38 ARCH-39 ARCH-41 | base:AUTH@2 ARCH@2 | dep:T017

## goal
GitHub and Google sign-in via Arctic that creates or links an account, issues the session cookie, and emits `AccountCreated`.

## acceptance
- [v] `GET /api/v1/auth/:provider` (github|google) → 302 to the provider authorize URL; `state` (and PKCE verifier for Google) stored in short-lived httpOnly cookies; an optional `returnTo` path is validated as a same-site relative path and stored too
- [v] `GET /api/v1/auth/:provider/callback` → exchanges the code, fetches the provider profile (GitHub: user + primary verified email via the emails endpoint; Google: id_token claims), then runs `SignInWithProviderUseCase`
- [v] use case resolution order: known `(provider, provider_user_id)` → load user · else verified provider email matching an existing verified identity → attach a new identity to that user (AUTH-5) · else create user + profile + generated handle and emit `AccountCreated` (AUTH-2)
- [v] an unverified provider email never links (creates a separate account); profile prefill = provider display name + avatar URL (AUTH-3), email stored on the identity only and never returned by a public endpoint (AUTH-4)
- [v] session created, previous session id for that browser rotated, cookie set `httpOnly, Secure, SameSite=Lax, Path=/, Max-Age=30d`; response 302 to `returnTo` or `/`
- [v] failure paths redirect to `/(sign-in)?error=<code>` rather than rendering JSON: state mismatch, expired/invalid code, provider error, provider account with no verified email
- [v] whole use case runs in one transaction (ARCH-38); `AccountCreated` dispatched after commit (ARCH-39)
- [v] auth routes throttled per IP (ARCH-41)
- [v] test: use case unit tests with in-memory repositories for all four resolution branches (known identity / link by verified email / new account / unverified email → new account) — asserting exactly one `AccountCreated` only in the create branches
- [v] test: state-mismatch and code-exchange-failure return the redirect with the right error code, and never create a user
- [v] test (int): full callback with the Arctic client stubbed — user, identity and session rows written, cookie attributes exactly as specified, second sign-in with the other provider on the same verified email attaches instead of creating

## impl notes
- Arctic handles authorize URL + token exchange only; profile fetching is a small per-provider adapter behind a `ProviderProfileFetcher` port so the use case stays provider-agnostic (ARCH-11)
- GitHub's primary email requires the `user:email` scope and a second API call; treat "no verified primary email" as a hard failure with its own error code — silently creating an unlinkable account would break AUTH-5 later
- config keys: `GITHUB_CLIENT_ID/SECRET`, `GOOGLE_CLIENT_ID/SECRET`, `OAUTH_REDIRECT_BASE_URL`
- session rotation on every sign-in (delete the old row if the cookie was present) ← cheap fixation defence
- `AccountCreated { userId, handle }` — the credit context subscribes in T021; nothing here knows about credits

- verified: `turbo run test lint typecheck build` 19/19 · domain+application coverage 92.3% lines · `api:contract:check` regenerated and committed · `pnpm test:docker` green · the real container answers `/api/v1/auth/github` with a GitHub authorize redirect and the state cookie, `facebook` and a stateless callback with their error codes
- arctic 3 is ESM only and this app compiles to CommonJS. `require()` of an ES module works on some Node builds and not others, so it is loaded with `import()` once inside the module's async factory, which keeps every client below synchronous. Its surface is declared by hand (a type import from ESM into CJS needs a resolution-mode attribute Biome cannot parse) and `arctic-module.test.ts` asserts the real package still matches
- GitHub secrets may not begin with `GITHUB_`, so the deploy carries `GITHUB_OAUTH_CLIENT_ID` and renders it as `GITHUB_CLIENT_ID` on the server
- the two providers end up with different strictness on an unverified email, exactly as the impl notes prescribe: GitHub with no verified address at all is a hard `AUTH_PROVIDER_EMAIL_UNVERIFIED`, while Google's `email_verified: false` proceeds and starts its own account (AUTH-5). If AUTH should treat them alike, that is an update-ssot
- the task's `ProviderProfileFetcher` is realized as `OAuthProviderClient.fetchProfile`: the authorize URL, the exchange and the profile are one provider's business, and splitting them across two ports would double the wiring for nothing
- when a provider hands over a display name or avatar the profile rules refuse, signup falls back to the generated handle rather than turning the person away at the door over a field they can edit later
- `state` is compared in constant time, and `returnTo` is accepted only as a same-site path — it ends up in a `Location` header
- not divergent from SSOT beyond the note above
